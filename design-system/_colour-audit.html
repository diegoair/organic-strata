1 · Summary

The one component already exists: Organica.palette.swatch, in two shapes — attach (one labelled row: 19 tools, 37 rows) and generate (the multi-colour chip strip, “RMX”: 8 tools). Plus two opt-ins: the “Pick from a palette” library menu and opts.pattern (FVS Paper only). We converge by extending it, not by starting over. Four problems:

Four kinds of colour control live outside it. The bare colour well in layer / channel cards and in variant rows (Camo Turing, Colornet, FVS, Trellis); “choose one of the current inks” (4 different UIs inside FVS); the mode / mapping block hand-copied in 5 tools; TuneSutra's editor.
Weak accessibility. Every row has an invisible tab stop (the hidden native input), three controls share one name, two tools announce a different name than the visible label, and the library menu ignores “one dropdown open at a time”.
The reference does not show what runs. /design-system/ has only static markup for the row and the chips: no well, no input, no library button.
The names disagree. 4 words for the foreground colour (Ink / Point / Mark / Dots), 4 for the ground (Paper / Background / BG / Color), 6 section titles, two spellings (Color / Colour).

6 · Proposal — one component, five variants

Same namespace Organica.palette, one new entry point; swatch() stays as an alias (string → single, element → inks), so no existing call breaks. Element ids and preset keys (cp-bg, rmx, state.bg) do not change.

Organica.palette.control(target, {
  kind: 'single' | 'well' | 'inks' | 'stops' | 'pick',
  role: 'ink' | 'paper' | '<custom>',      // visible label + every accessible name
  label, value | values, min, max,
  from: () => hexes, custom: true,           // 'pick' only
  modes: ['solid','adaptive','inks'], mapping: true,   // 'inks' only (D8)
  accessories: { library: true, random: false, none: false, pattern: {…} },
  onChange(value, detail), onCommit(value)    // onCommit = one Undo step (§7)
}) → { el, get, set, getColors, setColors, setActive, setPattern, destroy }

Parts every variant shares: the well (one tab stop; the native input gets tabindex=-1 + aria-hidden; name “‹Label› colour, #hex”) · the hex field (“‹Label› hex”) · accessories as .org-btn--icon (library, random, none / transparent, pattern). Buildable from JS as well as attached to existing markup. Every well opens the same picker (§7). The library menu joins organica:dropdown-open, gets arrow keys, takes its sizes from tokens.

7 · The colour picker

What it is today

Every colour in the suite is edited in the browser's native picker. The visible 18×18 swatch is a button that forwards its click to a hidden <input type="color"> (palette.js:150, cp.click()); a chip is a <label> around a real input. panel.css hides every colour input (opacity:0; position:absolute; pointer-events:none); the .color-swatch-wrap exists only so the invisible input sits under the swatch — Chrome anchors its popup to the input's rect. The component listens to input only (every drag step reaches the tool; there is no “commit”). Values are 8-bit sRGB hex only — no alpha, no OKLCH, even though shared/color.js has every OKLCH conversion, gamut mapping and contrast. 49 static colour inputs across ~20 tools, more built at runtime.

BrowserWhat the user gets
Chrome / Edge · macOSThe system Colors window (NSColorPanel): a floating OS window, not anchored, tabs for wheel / sliders / palettes / pencils, system eyedropper; alpha hidden.
Chrome / Edge · Windows, LinuxChromium's own popup anchored to the input: saturation/value field, hue slider, eyedropper, HEX / RGB / HSL readout.
Safari · macOSA small popover of suggested swatches + “Show Colors…” → the system Colors window. Since Safari 18.4 honours alpha and colorspace="display-p3".
FirefoxmacOS: the system Colors window · Windows: the old Win32 ChooseColor dialog · Linux: the GTK chooser.

Its limits

  1. sRGB hex only. No alpha, no wide gamut (except Safari ≥ 18.4 with the new attributes).
  2. No perceptual model at the moment of picking. The suite thinks in OKLCH (equal-lightness scales, contrast); the picker does not.
  3. OS-owned, not themable. Ignores data-theme and the tokens; looks different on every OS and browser (a floating window on macOS, an anchored popup on Windows Chrome, a 1990s dialog on Windows Firefox).
  4. The library, recent colours and contrast hints cannot live inside it — which is why “Pick from a palette” is a separate button.
  5. Fragile opening. .click() on an invisible input depends on its position; showPicker() is the sanctioned API (Baseline since 2022, allowed in cross-origin iframes for colour — relevant to Rhizome's bridges).
  6. No commit. Only input is listened to, so there is no clean Undo step; on macOS the Colors window keeps sending values after focus moved.

Where the platform is going: <input type=color alpha colorspace> ships in Safari 18.4+ only (not Chrome, not Firefox, Oct 2026) and still brings no OKLCH and no theming. The EyeDropper API is Chromium-only. Sources: MDN input color · showPicker · caniuse alpha · caniuse EyeDropper · WebKit, Safari 18.4 · Firefox QA.

What makes a picker simple for artists

  1. Swatches first: open on the palettes in use and the library; the free picker is the second step.
  2. Recent colours: the last 8–12 picks, shared across tools.
  3. Live while dragging, commit on release: one clean Undo step.
  4. Paste anything: #abc, abc, rgb(), oklch().
  5. Perceptual sliders: OKLCH lightness means the same across hues; show the gamut edge.
  6. Context: a contrast badge against the Paper (3:1 / 4.5:1) and “too close to ink n” (ΔE < 6).
  7. Old / new chip, eyedropper where it exists (hidden, not disabled, elsewhere), few modes.

Recommendation

(a) Keep native

Zero cost; OS-dependent UX, no theming, no OKLCH, library outside. Even if it stays: call showPicker() with click() as fallback, listen to change for commit / Undo, accept pasted CSS colours in the hex field.

(b) Our own popover picker — recommended

Built on shared/color.js + Organica.popover (Escape, outside click, focus return, one open at a time, both themes for free). Top: the palette library + recent row. Below: a 2D field + hue strip, HSB by default with an OKLCH toggle (gamut edge from color.maxChroma), hex paste, contrast chip against Paper, old / new chip, EyeDropper on Chromium, and “System picker…” → showPicker() as the escape hatch. ~6–10 KB, no dependency; ~1–2 days + ~1 day of cross-browser testing. Same onChange contracts, plus onCommit. Keyboard pattern modelled on vanilla-colorful (role="slider", arrows / Shift / PageUp / Home / End).

(c) Vendor a library

vanilla-colorful as the field + hue core inside our popover saves the fiddliest pointer / keyboard work, but it is HSV-only — the OKLCH plane would still be ours. Coloris is complete but brings its own DOM / CSS and no OKLCH. Avoid Pickr (frozen), iro.js (hiatus), Web Awesome / Spectrum (a second design system).

A new component: the design-system CONSULT gate applies before building. Facts from the sources above; the recommendation and the effort estimate are judgement.

8 · TuneSutra → tools: how palettes should reach the tools

Today

  • What TuneSutra stores: palettes in Organica.store('tunesutra'), keyed by name (Supabase key (user, tool, name)): colors[] hex, names[], ids[] (each colour has a stable c-xxxxxx id), locks, harmony, gradient, system. The palette itself has no stable id — saving under a new name writes a new record, so a rename would orphan any reference. Roles are positional (Base, Secondary, Accent, Accent 2…); there is no Paper or Ink role. Role shares come from color.roleShares (3 colours = 51 / 31 / 18 %).
  • What it exports: CSS custom properties --tunesutra-<name>-<step> for every 0–900 step, DTCG JSON (<name>.<step>, no role layer), gradient PNG / SVG, plates. The System view proposes chrome tokens for shared/tokens.css but is a proposal only — nothing loads it at runtime, by design (a saved palette must never break the interface).
  • How tools get it: palette.library() reads the local cache synchronously (your palettes + 3 built-in combinations + 21 Riso inks); palette.pick() pulls from the cloud once per page. The picked palette and colour are thrown away — only the hex is kept. Tool presets store plain hex.
  • When a palette changes later: nothing happens in the tools. No storage listener, no BroadcastChannel; store.onSync fires in the same tab only, so a tool open while you save in TuneSutra does not even see the new palette until reload.
  • Drift: the 3 built-in combinations are re-typed in palette.js and tunesutra/collections.js (different ids), held together by a comment. fvsField.palettes() is the only consumer that resolves roles automatically (by contrast). Rhizome's color port type is unused.

Recommendation — phased

  1. Phase 0 · hygiene, no UX change: a stable id on TuneSutra palettes (backfilled; the name stays the store key); generate the built-in combinations from collections.js (or test they match in check.py); refresh the library on storage events and window focus.
  2. Phase 1 · A + light C: “Use palette” in the picker fills a whole tool through a role map; copy by value, so presets and exports stay byte-stable; the last palette you chose in TuneSutra pinned at the top (“Suite palette”).
  3. Phase 2 · B, opt-in: linked colours with a Linked / Detached / Missing badge on the well; the hex is always stored and always used for export. Pilot in FVS (it already has roles and colourways) and Pollen.
  4. Phase 3 · as needed: DTCG import, a Rhizome Palette node, scale-step references.

Keep the System view a proposal — never wired live. Facts from the code (tunesutra/index.html, shared/palette.js, shared/store.js, shared/color.js, shared/fvs-field.js); options and phases are judgement.
