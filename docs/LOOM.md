# Loom — Universal Grid Generator — manual

`/loom/` — a universal layout-grid engine: every grid is generated from a common mathematical model, resolved once into a Universal JSON Model, then rendered by independent renderers (live HTML/CSS Grid, SVG, PNG, and — via the existing shared Figma pipeline — a Figma import). Not a column generator: the brief this was built from (`Grid Definition`, Notion) is explicit that this is a constraint-driven, multi-generator system meant to become an industry-standard layout tool.

**Status: Phase 1–4 and 6 complete, Phase 5 blocked, plus a convergence pass.** Every generator/preset item from the original brief shipped, then a direct review pass merged 6 pairs/trios that turned out to be the same mechanism at fixed parameter values into their surviving sibling (Voronoi→Organic, Modular→Bento+preset, Polar→Radial, Elliptical→Radial, Recursive→Fractal, Noise→Wave) — **15 generators live**, zero output capability lost (§4's own "Convergence pass" section has the full map and reasoning). Also live: the full pipeline below, a cross-tool grid-import path (`Organica.loadLoomGrid`, §3), a Figma export that reuses the existing SVG-import plugin as-is, **Phase 4** — per-side margins, real Kiwi edit-constraint use, and WYSIWYG drag-to-resize for the 5 rect-lattice generators (§7a) — and **Phase 6** — a Randomize control and this codebase's first automated test, `loom/_test-regression.html` (§7b). **Phase 5** (native Figma Auto Layout frames) is blocked, not started: the shared `Organica.sendToFigma()` channel every tool's own "→ Figma" button depends on turns out to go nowhere — the plugin never listens for the message type it sends — so there's no working channel to build native frames on top of yet (§8, flagged rather than fixed this session per Diego's own call).

## 1. Architecture

```
Canvas Manager (physical space: size, unit, margin, safe area, bleed)
     ↓
Grid Definition Engine (generator registry — js/generators/registry.js)
     ↓
Constraint Engine (per-generator: Kiwi solver OR direct parametric math)
     ↓
Universal JSON Model (js/json-model.js)  ← single source of truth
     ↓
Renderers: live CSS Grid · SVG · raster PNG · Figma (via shared pipeline)
```

Native ES modules (`loom/js/*.js`, `import`/`export`, no bundler) — the one deliberate deviation from every other Organica tool's single-file convention, chosen because this engine has a real module boundary (canvas → generators → solvers → model → renderers) that a 3000-line single file would obscure rather than simplify. `kiwi` and `Organica` are both classic global scripts loaded before the module entry point, read as unqualified globals inside the modules — same load-order pattern Camo Turing already uses for `Organica` inside its own `<script type="module">`.

## 2. The Kiwi / parametric split — the central architecture decision

Two solvers, chosen **per generator**, not globally — this was the explicit output of an architecture discussion before any code was written (the brief's own instruction: "Always explain architectural decisions before writing code").

- **Kiwi** (`shared/kiwi.min.js`, vendored — MIT/BSD-3-Clause, no CDN, same convention as Paper.js in Genesis Creator's Draw mode) — a real Cassowary constraint solver. Used where tracks should size **equally by default but be overridable under priority** — Bento today; every future modular/column/row grid, and Phase 4's WYSIWYG drag-to-resize, where dragging one track becomes a stronger edit constraint and the rest re-solve automatically, with no hand-written redistribution logic.
- **Parametric** (`js/constraint-engine.js`'s `solveTracksParametric`) — direct closed-form math, no solver. Used where tracks follow a continuous function that isn't a linear constraint — Sinusoidal today; every future radial/polar/noise generator.

`js/constraint-engine.js` exposes both; each generator picks the one that actually matches its own behaviour, documented in its own file rather than hidden behind a generic dispatcher.

## 3. Canvas Manager (`js/canvas-manager.js`)

Width/height/unit (px, mm, cm, or m), a preset library (`Square 1:1`, `Landscape 16:9`, `Portrait 4:5`, `Widescreen 3:2`, `A4 portrait/landscape`, `Letter portrait`), Margin and Safe area (both a single percentage of the canvas's own shorter side, applied to all four sides), and Bleed (always mm regardless of canvas unit — the real print convention — shown for any non-px unit).

**Units — px vs. the metric family.** mm/cm/m convert between each other with clean decimal factors (`UNIT_TO_MM = { mm: 1, cm: 10, m: 1000 }`); px does not — a CSS pixel has no fixed physical size, so "converting" it to mm would mean silently assuming a DPI nobody asked for. `createCanvas` canonicalises any mm/cm/m input to an internal **mm-equivalent** number (`canvas.width`/`canvas.height`) that every generator, `innerRect`/`safeAreaRect`, and the on-screen canvas-frame sizing read directly — none of them need to know or care which of the three the user actually typed. `canvas.displayWidth`/`displayHeight`/`unit` keep the raw typed number, unconverted, purely for showing it back to the user. Gap and Padding (absolute-number sliders, unlike the percentage-based Margin/Safe area) go through the same canonicalisation (`main.js`'s `unitVal()`) — and their own slider range/step rescales when the unit changes (`UNIT_RANGES`, `rescaleUnitField`), converting the CURRENT value to preserve its physical size rather than leaving the raw number unchanged and silently meaning something else (a Gap of "12" is 12mm under `mm` but would be 12 *metres* under `m` with no rescale — verified live that switching units keeps the physical gap constant, e.g. 12mm → 1.2cm → 0.02m, the last step-snapped by the `m` slider's own 0.02 granularity).

**Export unit suffixes.** SVG's and CSS's `width`/`height` need a real unit suffix on a physical canvas or the bare number is read as px — a genuine bug found while building this (an A4 canvas exported `width="210"`, i.e. 210px, not 210mm; the manual's own earlier claim that this already worked was wrong). Neither SVG nor CSS has a native **metre** unit, so any non-px unit — mm, cm, *and* m — exports as a literal `mm` suffix using the already-canonical mm-equivalent number (e.g. a 3m canvas exports `width="3000mm"`, dimensionally exact). `viewBox` and the grid's own internal CSS (`grid-template-columns`, `gap`, `padding`) stay bare canonical numbers rendered as px, matching the existing on-screen convention — only the outermost declared width/height carries physical meaning.

**Disclosed simplification**: per-side margins are a real brief requirement but deferred to the WYSIWYG-editing phase, since a per-side value wants a visual drag handle, not four more blind sliders. Safe area is a guide only in this phase — it doesn't clip generator output. On-screen preview treats 1 canonical unit as 1px regardless of the declared physical unit (no device-DPI-aware physical preview exists anywhere in Organica yet) — the exported file is always dimensionally correct even though the on-screen preview isn't physically true-to-size.

**Three canvas verification toggles** (`syncCanvasOverlays()` in `main.js`), all pure `#canvas-frame` CSS state, none of them touch the model and none are ever baked into an export (verified directly: exporting with all three on still produces `fill="none"` shapes and zero `repeating-linear-gradient` artefacts — the toggles are display-only, generated purely by the browser, not present in the model at all): **Background grid** — a translucent reference reticle, 12 divisions across the canvas's own width (density derived from the canvas, not hardcoded), drawn *above* the grid content rather than behind it — the initial version placed it behind and it was invisible, since every renderer's own opaque white background rect (needed for a standalone exported file) fully blocked anything underneath; fixed the same way a light-table guide layer sits above content in Photoshop/Illustrator. **Preview fill** — tints every cell with a faint colour, a direct visual proof that each cell is a real closed, fillable shape (the thing the SVG/PNG/HTML export fix above exists for) — implemented as one CSS rule overriding the polygon/rect `fill="none"` presentation attribute (CSS wins over SVG presentation attributes) plus the equivalent `background-color` for the CSS-Grid rect-cell path, so no renderer code needed to change. **Show numbers** — hides the number labels via CSS on both preview paths (`.loom-cell` text colour, SVG `<text>` display) rather than changing `main.js`'s own number-assignment logic, since hiding is a display concern, not a data one. Cell number font size raised from 9px/10px to 13px on both preview paths (CSS `.loom-cell`, SVG `<text>`) at the same request.

**Save grid — named presets + cross-tool import.** The brief's own stated workflow: define a canvas + grid in Loom, save it, then reuse that exact grid in any other Organica tool (or Figma/Affinity). Two pieces:

- **`Organica.presetStore('loom')`** (Save grid panel section) — the same shared named-preset store every other Organica tool already uses (`organica.loom.presets`), storing the FULL model (`buildModel()`'s own output — canvas, grid, cells), not a re-derivable subset. **Load** is a real round-trip, not just a re-display: `applyGridParamsToUI(type, params)` is the mirror image of `readGridParams()`'s own explicit per-generator branches (deliberately explicit rather than a naming-convention guesser — the same reasoning `readGridParams` already follows, since a few param names don't match their control IDs directly: Sinusoidal's `amplitude`/`frequency` → `rg-sin-amp`/`rg-sin-freq`, Radial's `innerRadiusFrac`/`startAngle` → `rg-radial-innerradius`/`rg-radial-startangle`). **Verified**: saved a Hexagonal grid (Rotation 30°, Spin mode Noise), switched to Bento, loaded the saved preset back — every control (including the two conditional Spin rows) re-synced to its exact saved value and the render matched pixel-for-pixel.

- **`Organica.loadLoomGrid(json)`** (`shared/organica-core.js`) — the cross-tool half: reads Loom's own JSON export (parsed or a raw string) and resolves it into absolute per-cell geometry — `{x,y,width,height}` rects for `cellShape:'rect'` grids, `{points,centroid}` polygons for `cellShape:'polygon'` grids — that any OTHER Organica tool can consume without knowing anything about tracks, spans, Kiwi, or Loom's own generator internals. Deliberately NOT an ES-module import of Loom's own `json-model.js` (ports the two small pure functions it needs — `innerRect`, `resolveCellRects` — instead): every other Organica tool is a plain single-file `<script>` with no bundler, the same reason every polygon generator in `loom/js/` already keeps its own private copy of `clipToRect` rather than sharing one. Throws a plain, user-safe `Error` (not a stack trace) on invalid JSON or a non-Loom object, matching the "never let a bad file import crash the host tool" discipline every file-input handler elsewhere in Organica already follows. **Verified**: real exports from both a rect-cellShape grid (Bento, 10 cells) and a polygon-cellShape grid (Hexagonal, 67 cells) round-tripped through `loadLoomGrid` correctly; a malformed-JSON input threw the expected clean error message rather than crashing.

- **Both cross-tool behaviours the brief names are now concept-proven**, neither shipped into a host tool yet — kept in the repo (not linked from the hub) as reference for that later integration work, one per behaviour plus the earlier per-cell-generation concept test:
  - **`loom/_test-camo-cells.html`** — the very first concept probe, before the loader existed: a plain 3×3 Bento grid, each cell running its own independent Gray-Scott reaction-diffusion sim (Camo Turing's own verified f/k presets, CPU-ported). Established that a grid cell CAN be an independent generative container at all, before the cross-tool plumbing (`loadLoomGrid`, Save grid) existed to make it a real workflow.
  - **Slice & Reposition** (`loom/_test-slice-reposition.html`) — the tool-agnostic one: export a real grid from Loom, load it via `Organica.loadLoomGrid` in a separate page, and use its resolved cell geometry to slice+reposition an external image (a "puzzle remix": each cell samples a corresponding — optionally shuffled — fractional region of a source image and redraws it into that cell's own clipped shape). Verified on both rect and polygon cellShapes, faithful-slice and shuffled modes alike.
  - **Mix & Restructure** (`loom/_test-mix-restructure.html`) — the deeper, per-tool-integration one: each cell runs its OWN independent generative pass, not a shared crop. Ported Spore's real placement algorithm (`spore/index.html`'s `doRender()` — a hex-jittered lattice, mark size driven by local image darkness, points below `luma > 0.92` skipped) faithfully for the lattice/sizing math, simplified the mark itself to plain circles rather than replaying a full Genesis SVG symbol (disclosed, not hidden — that needs `organic-forms.js`'s mark data, a bigger dependency than a concept test needs). Each cell independently samples its own sub-region of one shared source image and runs its own stippling pass with its own spacing/size/rotation — cycled through a small fixed preset list by cell index (reproducible, not random-every-render) rather than truly random, so results can be verified. Verified live on both a 3×3 Bento grid (9 cells) and a Hexagonal grid (45 cells): "Vary structure per cell" shows genuinely distinct textures per container while still faithfully tracking the source image's own luminance; "uniform structure" (identical spacing/size/rotation everywhere) reads as one continuous pattern only interrupted by the clip shape, the correct baseline contrast — proves a grid cell can be a real independent generative container, the concept this whole thread of work set out to test, not just a crop window with a fancy border.

  Both prototypes share the same architecture: `Organica.loadLoomGrid` for the grid, an offscreen canvas per cell for the corresponding source-image sub-region, `ctx.clip()` to the cell's own shape (rect or polygon) before drawing. Zero console errors on either, across every generator/mode combination tested.

### Bento (`bento.js`) — Kiwi

A base Columns×Rows lattice where adjacent cells are randomly merged (seeded) into 1×1 up to 2×2 rectangular spans — the mixed-size look a Bento grid is named for. `Variety` gates how often a merge is attempted; **0 is a verified exact no-op** (a plain uniform grid, every cell 1×1). Track sizing is solved by Kiwi: every column/row equal by default (medium-strength constraint — a soft preference), a hard minimum size, and a hard "tracks + gaps fill the canvas" sum.

A first version weighted each track by how many spans touched it, meant to make a track under a wide cell size up proportionally — reverted after testing, because dividing a wide cell's contribution across its own tracks made them *thinner*, the opposite of the intended effect. Bento's visual variety comes entirely from the span topology, not from unequal track sizing.

### Wave (`sinusoidal.js`, type key `sinusoidal`) — parametric

A full Columns×Rows lattice, no merged spans — the rhythm here is in **track size**, not topology. `Function` (Sine/Noise, merged from what shipped as two separate generators — see the convergence table above) picks the weight formula: Sine follows `1 + Amount · sin(t · Frequency · 2π + Phase)`; Noise follows `1 + Amount · (2·fbm(t·Scale, seedOffset) − 1)`, `Organica.noise.fbm` sampled along a line (`constraint-engine.js`'s own header named this exact extension point — "sine, noise, radial, polar…" — when Sinusoidal first shipped). Either way the result is a relative weight, rescaled to fill the canvas exactly (`solveTracksParametric`'s normalise-then-rescale, the same shape Warping's own pattern functions use). `Amount` is shared by both functions (0 = uniform tracks, exact no-op either way); Sine-only rows (Frequency/Phase) and Noise-only rows (Scale/Seed) show only for their own Function, same conditional-row discipline as Hexagonal's own Spin-mode rows. Columns and Rows get two DECORRELATED noise curves from one seed when `Axis: Both` and `Function: Noise` (different fixed y-offsets into the shared 2D field, the same trick Warping's own domain-warp taps use) — verified live: the exported track arrays are genuinely different sequences, not the same curve read twice.

**Honesty note** (same discipline as Camouflage's "Stripes/worms" disclosure): this modulates track *size*, not track *boundary shape*. A literal wavy/organic grid line isn't representable in real CSS Grid (`grid-template-columns` is a list of straight sizes) or as an axis-aligned SVG rect grid, so "Wave" here means a rhythmic or irregular width/height sequence — honestly renderable by every promised target, rather than a wavy-edged or torn-paper grid the CSS renderer could never actually deliver.

**Verified**: Function Sine reproduces the old Sinusoidal generator's own exact track output at matching params; Function Noise reproduces the old Noise generator's own exact output; Frequency/Phase rows hide and Scale/Seed rows show the moment Function switches to Noise, and back; Amount 0 is an exact no-op under either function.

**Grid-type icon fixed** (caught by Diego, not by testing): the thumbnail used a literal sine-curve glyph, which is actively misleading — Wave only ever modulates track *size* (see the Honesty note above), it never bends a boundary into a visible curve, so a wave-shaped icon promised something the generator structurally cannot deliver. Replaced with an "uneven bars" glyph (5 vertical lines of varying height) that actually represents what the generator produces.

### Hexagonal (`hexagonal.js`) — geometric

The second polygon-shaped generator, and proof the `cellShape: 'polygon'` fork Voronoi introduced generalises for free: this file only had to produce cells shaped `{ points, centroid }` — every renderer (SVG/PNG export, the embedded-SVG live preview) already branches on the flag, so nothing outside `hexagonal.js`/`registry.js`/the panel block changed to add it.

Real regular-hexagon tessellation (the standard redblobgames flat-top axial-spacing formulas — `1.5r` horizontal / `√3·r` vertical, odd columns offset by half a row), not a distorted hex-ish shape. `Columns` sets the target horizontal spacing (`inner.width / cols`), from which the hexagon radius and both spacings are derived — density, not a literal hex count, so the same slider value behaves consistently on a square canvas or a wide banner. `Gap` shrinks each hexagon toward its own centre before clipping (the polygon analogue of rect-cell Padding, applied pre-clip since a polygon has no separate track size to shrink into) — **verified 0 is an exact no-op**: edge-to-edge tessellation, single de-duplicated boundary line, no doubled-stroke artefact. `Jitter` offsets each hexagon's centre by a seeded random amount before the polygon is built, breaking the lattice into an organic hand-set-tile look (verified visually: overlapping, unevenly-spaced hexagons at Jitter 0.7, vs. a perfect grid at 0).

**`Rotation` (0–60°), not a Flat-top/Pointy-top toggle.** The original ship used a two-way segmented control; replaced same-session per Diego's own request for a continuous control, since the toggle's two options were never really a binary — "pointy-top" IS "flat-top" rotated 30°, and a rigid hexagonal tiling tiles at *any* angle, not just those two. The naive version of this — rotate each hexagon's own SHAPE while leaving the lattice centres fixed — is wrong: a hexagon's edges only meet its neighbours' edges when the shape's orientation matches the lattice's, so a shape-only rotation opens visible gaps/overlaps at any angle that isn't a multiple of 60°. The fix is to rotate the CENTRES and the SHAPE together, a rigid rotation of the whole pattern, which the honeycomb's own rotational symmetry guarantees still tiles at every angle. Implementation: the lattice is built in its own unrotated frame first (sized from the inner rect's own diagonal, not its width/height, so a rotated lattice still covers every corner of the actual — unrotated — inner rect), rotated as a whole around the inner rect's centre, then clipped against the real axis-aligned inner rect. The control's range is exactly `[0, 60)` because that's the hexagon's true rotational period (0 = the old "Flat-top", 30 = the old "Pointy-top") — anything past 60° just repeats. **Verified**: 0° and 30° reproduce the old two named orientations pixel-for-pixel; an in-between angle (15°) tiles the whole canvas edge-to-edge with zero gaps/overlaps, confirmed visually and via a real de-duplicated SVG export (220 `<line>`s on a 73-cell canvas); Gap 0 stays an exact no-op at every rotation tested.

**`Spin mode` / `Spin amount` — per-CELL rotation, a deliberately different control from `Rotation`, not a finer-grained version of it.** Diego's own follow-up: "what if we rotate each individual hexagon?" `Rotation` rotates centres and shapes *together* (rigid, tiling-preserving, above); Spin rotates only each hexagon's own local orientation on top of that — which by definition can't preserve edge-to-edge tiling once neighbours stop facing the same way, the same honest trade-off `Jitter` already makes for position. Since "rotate each hexagon" doesn't name one specific effect, structurally different generators of the idea were built across two rounds (asked, not guessed, since they don't converge visually the way colour presets do) and exposed as a `Spin mode` dropdown (Off/Random/Checkerboard/Radial/Spiral/Noise — a dropdown rather than a segmented control, since word labels don't fit more than ~3 short options in a 248px panel without truncating, caught live before shipping): **Random** — seeded, uniform in `[-Amount, +Amount]` per cell, a fractured hand-set-mosaic look. **Checkerboard** — alternates `±Amount` by `(col+row)` parity in the lattice's own unrotated indices, a deterministic woven pattern, not random. **Radial** — `Amount` scaled by each cell's distance from the inner rect's centre (0 at centre, full `Amount` at the corners), a continuous "unfurling" gradient. **Spiral** — `Amount` scaled by each cell's *angle* around the centre (`atan2`, not distance), a true pinwheel/vortex twist; angle wraps at ±π so there's a real, intentional seam where Spin jumps from `-Amount` to `+Amount` — disclosed rather than smoothed away (smoothing it would make it a wave, a different mode). **Noise** — `Amount` scaled by a seeded 4-octave value-noise field (`Organica.noise.fbm`, `shared/organica-noise.js` — Loom's first consumer of the shared noise module, ported rather than a fourth private copy after Komorebi/Camo Turing/Warping) sampled at each cell's centre, an organic wind-blown texture; the one mode with its own second control, `Noise scale` (cycles of the field across the canvas), since "how chaotic" and "how big are the swirled regions" are independent knobs. Applied to each hexagon's own local vertex angles *before* the rigid `Rotation` step, so Spin composes correctly with Rotation instead of fighting it. `Off` (default) is an exact no-op — Spin Amount is hidden whenever Off is selected, `Noise scale` shown only for Noise, same dead-control-avoidance rule as Voronoi/Bento's own conditional rows.

**Two real bugs found during verification of this round, both fixed, neither caused by the geometry itself:** (1) `window.syncHexSpinRow` was never exported in `main.js`'s own window-export block, so the Spin mode dropdown's inline `onchange` handler threw on every real switch — invisible in an earlier verification pass only because that pass checked a fresh tab's console *without* actually exercising a mode switch in it (a proxy check, not the real one); fixed by adding the missing `window.syncHexSpinRow = syncHexSpinRow` line, then re-verified by switching through all 6 modes in one pass with a clean console throughout. (2) Independent of Spin entirely: a *fresh Loom load* — plain default Bento, zero interaction — was landing at 1% zoom, fully off-screen, because `fitToViewIfNeeded`'s very first call (synchronous, at module init) could read `canvas-wrap`'s `clientWidth` before its own layout had settled, went negative once the 64px margin was subtracted, and that negative "available space" fed a negative scale into `zoomBy` which the zoom-pan module's own floor clamps to 1%. Fixed by retrying on the next animation frame (without committing `lastFitKey`) whenever the measured available space isn't yet positive, instead of fitting to garbage dimensions — verified a fresh load now lands at a sane fit (57% in the tested viewport) with no manual reset needed.

**Verified**: Off reproduces the pre-Spin render pixel-for-pixel; all five active modes render as visually distinct (Random = fractured, Checkerboard = regular alternation, Radial = smooth centre-to-edge gradient, Spiral = pinwheel with an honest seam, Noise = organic spatially-coherent wobble); SVG export still real vector geometry in every mode (384–388 `<line>`s on a 67-cell canvas, mostly no-longer-deduped, correctly, since neighbouring edges stop aligning once spun); 0 of the block's controls unaccessibly-named; all four generators × all six Spin modes regression-clean, zero console errors confirmed by actually exercising every mode switch, not just loading the page.

**Diego caught a real dead-control gap by asking to check Seed specifically, later the same day**: with Jitter 0 and Spin mode Noise, changing Seed had zero effect — `Organica.noise.fbm` has no seed parameter at all, so unlike Random (genuinely seeded) or Checkerboard/Radial/Spiral (genuinely deterministic by design, correctly seed-independent), Noise's insensitivity to Seed was neither. Fixed by sampling `fbm` at a per-generation `(x,y)` offset drawn from a SECOND, independent `mulberry32` stream (seeded from a distinct transform of `seed`, `seed ^ 0x9E3779B9`) — deliberately never sharing draws with the main `rng` that feeds Jitter/Random, so the fix couldn't perturb either of those at a fixed seed. Ported identically to Triangular and Diamond, since all three share the exact copied `spinFor`. **Verified**: Noise now genuinely differs across Seed values on all three generators (confirmed by diffing the exported JSON model, not just eyeballing it); Random's own seed-dependence unaffected on all three; all seven generators regression-clean, zero console errors.

Clipping reuses the same Sutherland–Hodgman technique as Voronoi's own `clipHalfPlane`, generalised from one half-plane per neighbour seed to 4 fixed half-planes (the inner rect's own edges) — a hexagon straddling the inner-rect boundary is trimmed to a real partial polygon, not dropped or left overflowing. Verified end to end: both orientations render correctly, Gap/Jitter/Columns/Seed all rebuild live, SVG export contains real de-duplicated polygon-edge geometry (276 `<line>` segments on a 95-cell canvas, not a degenerate fallback), all four generators (Bento/Sinusoidal/Voronoi/Hexagonal) regression-tested together with zero console errors, 0 of the block's controls unaccessibly-named (the two orientation segmented buttons carry their own visible text, same convention as every other `seg-ctrl` in Loom).

### Radial (`radial.js`) — geometric

The third polygon-shaped generator, and a genuinely different STRUCTURE from both families before it, not another variation of an existing one — Bento/Wave are a Columns×Rows track lattice, Hexagonal/Triangular/Diamond/Circular are a tessellation of one repeated cell shape; Radial is real polar coordinates, concentric Rings crossed with angular Sectors, each cell a curved ring-sector wedge — the dartboard/sunburst/mandala structure neither of the other two families can honestly produce. `cellShape = 'polygon'` again, but each cell's two curved edges are approximated as short line segments (roughly one vertex per 10° of arc) rather than the 3–6 straight edges every other polygon generator emits — a real arc has no exact polygon form, so it's subdivided finely enough to read as smoothly curved at any reasonable Rings × Sectors count.

**Now also covers the old Polar and Elliptical generators** (see the convergence table above), via two controls orthogonal to everything else: `Radius curve` (1 = linear ring spacing, Radial's own original behaviour; curve>1 bunches thin rings near the centre, a dartboard/iris-like density gradient; curve<1 bunches them toward the outer edge) and `Stretch to canvas` (off = a circle inscribed in the canvas, Radial's own original boundary; on = an ellipse touching all four edges instead, scaled independently per axis — the old Elliptical's own case, which used to leave real margin space on the long axis of a non-square canvas when off).

**No inner-rect clipping needed**, unlike Hexagonal/Triangular — genuinely simpler, not a shortcut: the whole radial field is built inside the outer ring boundary (a circle or ellipse depending on `Stretch`), so every wedge is guaranteed to land fully inside it by construction. `Inner radius` (0–0.8, fraction of the outer radius) is the dartboard/donut-chart control — 0 gives true pie-slice wedges at the innermost ring, the "inner arc" degenerating to a single point at the centre through the *same* arc-point code (not a special case): every point on a near-zero-radius arc just lands at the centre, drawing as a zero-length segment for free. `Gap` insets each wedge inward on both its radial and angular sides before the arc is built — the same "shrink toward the cell's own middle" idea as Hexagonal's own Gap, with two independent inset amounts since a wedge has two genuinely different kinds of edge. `Start angle` rotates the whole field. At Gap 0 this tiles edge-to-edge exactly (concentric circles/ellipses + radial spokes, single de-duplicated lines throughout), the same "0 = true no-op" discipline as every other Organica control.

**`Distortion` (Off/Sine/Noise)**, part of the same rollout as Linear's own Distortion (below) onto every generator where the separable-warp trick cleanly generalises. Radial bends BOTH edge families at once through one shared `realPoint(R, A)`: spokes (radial edges) wobble in ANGLE as a function of radius only, rings (arc edges) wobble in RADIUS as a function of angle only — the identical separability argument Linear's own header makes in full, since a ring's own nominal R is fixed along its whole length (every ring gets the same angle-nudge) and a spoke's own nominal A is fixed along its whole length (every wedge gets the same radius-nudge), so shared edges stay coincident with no seam-matching special case. Active distortion also sets `cell.smooth: true`, so export/preview draw a real Catmull-Rom curve through the sampled points instead of visible straight-segment facets (see json-model.js's own `catmullRomPathD`, §5). **Verified at Amount 0.5 (default) numerically, not just visually**: sampled the outer ring's own max radius across all 12 sectors and found genuine per-sector variance (470–500px, a real ~6% wobble, non-uniform) — the low default Amount reads subtly at this cell density, which is why an earlier pass mistook it for "not working"; confirmed unambiguously by raising Amount to 0.9, which renders an obvious wobbly-ring / twisting-spoke mandala in both Sine (clean flower/vortex pattern) and Noise modes. Lesson: numeric confirmation of the underlying data, not just a glance at a subtle-by-default render, is what actually settles whether a distortion control is live.

### Triangular (`triangular.js`) — geometric

The fourth polygon-shaped generator — real equilateral-triangle tessellation (alternating up/down triangles via the standard `h = side · √3⁄2` row-height construction), not a rectangle-cut-in-half approximation, which only tiles at 90°/45° and reads as a cut rectangle rather than a triangular mesh. `Columns` sets the target triangle side length (`inner.width / cols`), matching Hexagonal's own density-not-count convention. **Genuinely does need inner-rect clipping**, unlike Radial and unlike this file's own first-draft doc comment claimed before being corrected during the same build — Radial's field is inherently bounded by its own outer radius by construction, but a plain triangle row/column loop has no such built-in boundary, so boundary triangles are trimmed with the same Sutherland–Hodgman `clipToRect` Hexagonal already uses (each polygon generator keeps its own private copy rather than sharing one, the established pattern in this file set). `Gap` shrinks each triangle toward its own centroid (same idea as Hexagonal's own Gap); `Jitter` offsets each triangle independently before the shrink, the same accepted "neighbours stop sharing an exact edge" trade-off Hexagonal's own Jitter already makes, rather than the more involved shared-lattice-vertex jitter a "real" irregular triangulated mesh would use — deferred as a future refinement, not attempted this round. At Gap 0 / Jitter 0 this tiles edge-to-edge exactly.

**`Rotation` and `Spin mode`/`Spin amount`/`Noise scale` — ported verbatim from Hexagonal**, same session, same request applied to the new generator. `Rotation` (0–60°) is the identical rigid whole-lattice rotation: the triangular lattice is the hexagonal lattice's own dual and shares its 6-fold symmetry, so the field is built in its own unrotated frame (sized from the inner rect's diagonal, centred on its centre), rotated as a whole, then clipped — rotating each triangle's shape alone while leaving lattice points fixed would reopen the same gaps/overlaps Hexagonal's own header explains. `Spin mode` offers the identical five flavours (Random/Checkerboard/Radial/Spiral/Noise), rotating each triangle's own local orientation around its own (jittered) centroid, independent of and composed before the rigid `Rotation` — same "necessarily breaks tiling" trade-off as Jitter. Composition order: jitter (position) → spin (local orientation) → gap (shrink) → rotation (rigid, whole-field) → clip.

**Verified**: Gap 0 is an exact edge-to-edge no-op (clean zig-zag boundary, single de-duplicated lines, correctly clipped on all four sides — no overflow past the inner rect); Jitter 0.5 produces a genuinely distinct scattered-triangle texture; Rotation 0 reproduces the pre-Rotation render exactly (170 cells, identical layout); Rotation 30 still tiles perfectly edge-to-edge at a visibly different diagonal angle; all six Spin modes (Off/Random/Checkerboard/Radial/Spiral/Noise) render distinctly with correct row visibility (Spin amount hidden only at Off, Noise scale shown only at Noise); Noise mode shows the same organic spatially-coherent wobble as Hexagonal's; SVG export real vector geometry (544–576 `<line>`s depending on config); 0 unaccessibly-named controls; all six generators regression-clean with the console watched live through every actual mode switch in the same tab.

### Diamond (`diamond.js`) — geometric

The fifth polygon-shaped generator, and the cleanest illustration yet of "rotate the whole field, never just the shape" — squares built on a PLAIN uniform lattice (no offset math at all, trivially edge-to-edge: `hSpacing = vSpacing = side`), each square's own 4 vertices placed at its corners (45°+90°·i) so `Rotation` 0 reads as a plain axis-aligned square grid and `Rotation` 45 reads as the classic diamond/argyle pattern — one continuous `[0, 90)` control (a square's point-group order is 4, not 6, hence the different period from every other polygon generator here) morphing between what would otherwise be two separate named generators. Ships with `Rotation` defaulting to 45, not 0, so it reads as "Diamond" out of the box per its own name, while still being freely adjustable down to plain squares or anywhere between.

**A real first-draft mistake, caught and rebuilt before ever running the code**: the first attempt built diamond-oriented squares directly on an OFFSET row/column lattice, guessing at spacing by analogy to Hexagonal's own offset-row construction. Re-deriving the geometry by hand (checking where same-row diamonds' vertices actually landed) showed adjacent diamonds only touched at a single VERTEX, not a shared EDGE — real gaps between rows, not a valid tiling, caught by re-checking the reasoning rather than by a failed render. Fixed by dropping the hand-derived diamond-lattice spacing entirely and building what's actually proven to tile — a plain square grid — then applying the exact same "rotate the whole field rigidly" mechanism already proven correct by Hexagonal and Triangular. A rigid rotation of a tiling that already tiles is still a tiling, at any angle, with zero new spacing math to get wrong.

`Spin mode`/`Spin amount`/`Noise scale` are the identical five flavours as Hexagonal/Triangular, ported the same way, applied to each square's local orientation before the rigid Rotation.

**Verified**: Gap 0 is a true edge-to-edge no-op (continuous zig-zag lines throughout, confirmed visually after the lattice-geometry fix — this was the exact property the first draft got wrong); Rotation 0 renders a clean, correctly-counted axis-aligned square grid (81 cells on a 9×9 canvas at the default density); Rotation 45 renders the diamond/argyle pattern; an in-between angle (20°) tiles perfectly with no gaps; Noise Spin mode shows the same organic wobble as the other two generators; SVG export real vector geometry (340 `<line>`s on an 85-cell Noise-spun canvas); 0 unaccessibly-named controls; all seven generators (Bento/Sinusoidal/Voronoi/Hexagonal/Radial/Triangular/Diamond) regression-clean, console watched live through every actual switch.

### Circular (`circular.js`) — geometric

The seventh polygon-shaped generator, and a second first-draft correction caught by Diego rather than by testing: the initial build clipped a plain rect lattice inside a circular BOUNDARY (a grid of squares that happens to sit inside a circle) — wrong, because it means the base CELL shape stayed a square, when every sibling generator's own naming convention is that the cell itself is the named shape (Hexagonal's cells are hexagons, Triangular's are triangles, Diamond's are squares). Rebuilt so each cell genuinely IS a circle: a real circle-packing grid, centres on the identical triangular/hex-packing lattice as Hexagonal's own offset-row construction (not a coincidence — a hexagonal tiling's centre lattice and a circle-packing's centre lattice are the same lattice), with different spacing constants since circles pack point-TANGENT rather than edge-to-edge: same-row centre spacing is the full diameter `d`, row spacing `d·√3⁄2`, odd rows offset by `d/2`.

**Honesty disclosure, the same kind of thing Sinusoidal's own header states for wavy boundaries**: circles cannot truly tessellate the plane the way every other shape in this file set can — at Gap 0 circles touch their neighbours at a single point, not a shared edge, so real triangular voids remain between any three mutually-touching circles. That's correct circle-packing geometry, not a bug — every circle's own outline draws as its own closed `<polygon>`, independently. `Columns` sets the target diameter (`inner.width / cols`); `Gap` shrinks each circle's radius from the touching size. Inner-rect clipping is needed, same reason and same technique as Hexagonal/Triangular/Diamond — boundary circles trim into real partial-disc shapes at the canvas edge.

**Verified**: Gap 0 shows circles genuinely touching (maximum packing, visible triangular voids between neighbours, not overlapping and not gapped); Gap > 0 opens visible space between circles cleanly; SVG export real vector geometry (3579 `<line>`s on a 95-cell canvas — high count is expected and correct, since circles don't share edges to dedup); 0 unaccessibly-named controls; all eight generators (Bento/Sinusoidal/Voronoi/Hexagonal/Radial/Triangular/Diamond/Circular) regression-clean, console watched live through every actual switch.

**`Rotation`/`Jitter`/`Seed`**, added same session per Diego's own follow-up ask. `Rotation` (0–60°, the hex-packing lattice's own period) rigidly rotates the whole lattice of centres, built the identical proven way as Hexagonal/Triangular/Diamond (unrotated frame sized from the inner rect's diagonal, centred on its centre, rotated as a whole, then clipped) — the one honest wrinkle specific to Circular: a circle's own outline is rotationally symmetric, so Rotation never changes an individual cell's SHAPE, only how the rows/columns align relative to the canvas, which changes how the boundary clips (visibly different diagonal cuts at the edges, confirmed at Rotation 30°). `Jitter` offsets each circle's centre by a seeded random amount before clipping, same accepted trade-off as every sibling generator's own Jitter — circles can end up overlapping or unevenly spaced, a hand-scattered "pebble/bubble" look instead of mechanically perfect packing (verified visually at Jitter 0.4).

### Linear (`linear.js`) — geometric

Shipped first as two separate generators, Column and Row (each a single fixed axis, `count`/`gap` only) — then combined into one on direct request, since two fixed-axis generators with no other controls meant "rotate the columns" or "make it columns-and-rows together" had nowhere to go. Linear replaces both: `Axis` (Columns / Rows / Both) picks which of Column's/Row's/a Modular-like 2D lattice's own topology it reproduces, and `Rotation`/`Jitter`/`Seed` are the same controls Hexagonal/Triangular/Diamond/Circular already carry, generalised to a rectangular (not necessarily square) cell.

This forced a real representation change: Column/Row started as `cellShape: 'rect'`/Kiwi-solved (live CSS Grid), but Rotation needs `cellShape: 'polygon'`/geometric instead — CSS Grid has no way to rotate individual tracks independently, and clipping a rotated lattice to the canvas rect at the boundary needs real polygon geometry (the same reason Diamond isn't a CSS Grid generator either). Two orthogonal rotated basis vectors (`nx1`/`nx2`) do all three Axis modes with one shared cell-builder: `both` places a small `sx×sy` rect at every lattice point; `cols`/`rows` place a STRIP — full track width but stretched `halfLen` (≈ the canvas diagonal) along the other axis, then clipped — so the same corner-offset math naturally reproduces Column's full-height strips, Row's full-width bands, or a 2D lattice, never three separate code paths.

**Verified**: Rotation 0/Gap 0/Jitter 0 reproduces an exact axis-aligned rect lattice byte-for-byte (checked the first cell's own 4 corners against the expected inner-rect math, not just eyeballed); Rotation 25° on Axis Columns fills the canvas edge-to-edge with rotated, clipped strips (no gaps, no overflow); Axis Both at the same rotation shows both Columns/Rows sliders and tiles a real rotated 2D lattice cleanly; the built-in **Timeline** preset (below) now targets `linear` with `axis: 'cols'` and loads correctly. `column.js`/`row.js` deleted, not left as dead files.

**`Distortion` (Off/Sine/Noise) — bends the division LINES themselves, not just track sizes.** Asked directly and analysed before building: this is honest on Linear in a way it structurally cannot be on Wave. Wave is `cellShape: 'rect'` (real CSS Grid tracks), so its own header discloses it can only ever modulate track SIZE, never the boundary's shape. Linear has been `cellShape: 'polygon'` since Rotation shipped — its cells are already plain point lists, not CSS Grid tracks — so a division line becoming a real curve costs nothing architecturally.

The construction that makes this work without seams: `warp(offX, offY)` — ONE function used for every point on every edge of every cell — returns a lateral displacement whose X-component (`Dx`) depends ONLY on Y, and whose Y-component (`Dy`) depends ONLY on X. This separability is what guarantees two neighbouring cells always compute the IDENTICAL warped position for a shared boundary, from either side, with no seam-matching special case needed: a shared vertical edge has a literally-constant Y-offset for both of its neighbours, so both evaluate the same `Dx(that constant Y)`; a shared horizontal edge works the same way in the other axis. Straight nominal lines (in unwarped offset-space) are subdivided (32 samples for a strip's full length, 6 per side for a small Both-mode cell — coarser there only to keep point counts sane on a large Cols×Rows grid) and each sample passed through `warp` — at `Distortion: Off` the subdivision drops to 1 (a plain straight segment), reproducing the pre-Distortion output exactly, not just visually close.

Sine: `Amount·spacing·sin(t·Frequency·2π + Phase)`, `t` = position along the line's own length divided by the relevant canvas dimension (same "Frequency = cycles across the canvas" convention Wave already uses). Noise: `Organica.noise.fbm` sampled along the line (`t·Frequency` as the field coordinate) — Phase hidden for Noise, same reasoning as Wave's own Phase row (fbm has no phase to speak of). `Amount` 0 or `Distortion: Off` are both exact no-ops. Padding around the lattice (`extra()`) got a small bump (+3 instead of +1 spare strip) since a wavy/noisy line's own lateral excursion can otherwise leave the same kind of corner gap Rotation's own coverage fix (above) already had to solve once.

**Scoped first to Axis Columns/Rows, per direct instruction, then extended to Axis Both and verified the same way** — the `warp()` separability argument applies unchanged to Both (each small cell's 4 sides are just shorter subdivided edges through the identical function), so no separate code path was needed for it, only the one shared construction. **Verified**: Sine on Columns renders genuine sine-wave strips, confirmed visually (smooth, evenly-spaced waves) and structurally (`Distortion: Off` keeps exactly 4 points per cell; Sine active correctly produces many more, clipped down at the canvas edge as expected); Noise on Rows renders organically wavy horizontal bands with the same seam-free tiling; Rotation 25° + Distortion together still cover all four canvas corners with no gaps (the padding bump verified doing its job); **Axis Both at Gap 0 shows genuinely seamless tiling** — screenshot-verified with zero visible gaps or overlaps across the whole lattice, the most sensitive case for revealing any inconsistency in the warp construction, none found; SVG export real closed `<polygon>` shapes matching the cell count exactly in every mode tested; all 15 generators regression-clean at their (Distortion-off) defaults; Randomize stress-tested 4 rounds × all 15 generators including Linear's own new Sine/Noise/Off cycling, zero exceptions; `loom/_test-regression.html` confirms all 15 pass; 0 of 125 panel controls unaccessibly-named; zero console errors throughout.

### Rectangular (`rectangular.js`) — parametric

The asymmetric/hierarchical sibling to Modular: still a plain lattice, no merged spans, but track sizes come from explicit user-typed ratio strings ("2,1,1") instead of being equal (Modular) or following a periodic/noise function (Sinusoidal/Noise) — the classic content-driven magazine grid, one wide lead column next to narrow ones, a proportion neither a uniform rule nor a periodic wave can express. Solved by the same `solveTracksParametric` every parametric generator already uses — the parsed ratio array IS the `sizeFn` weight, no new solving strategy needed. Column/row COUNT is derived from how many numbers are typed, not a separate slider, so the text field is the only thing that can change topology — there's never a mismatch between "how many tracks" and "how many ratios" to reconcile.

### Diagonal (`diagonal.js`) — geometric

Diamond's own parallelogram sibling: Diamond is a plain square lattice rigidly ROTATED as a whole field (its two edge families are always exactly 90° apart); Diagonal exposes that inter-family angle itself as `Skew`, so the cell shape genuinely changes — square → rhombus → increasingly sheared parallelogram — rather than only spinning. Two families of parallel lines is exactly what an affine-sheared regular lattice already is, so no separate line-intersection code was needed: each cell is the parallelogram spanned by two basis vectors `u` (at `Angle`) and `v` (at `Angle + Skew`) from a lattice point, the direct 2D generalisation of Diamond's own "build what already tiles, then transform the whole field" construction. `Skew = 90` reproduces a plain rotated rect lattice exactly (Diamond's own case); away from 90° it shears into genuine rhombi no other generator here can produce.

**Verified**: Skew 90/Angle 20 renders as a plain rotated grid, matching Diamond's own Rotation-0 case visually; Skew 50 produces genuinely sheared parallelogram (rhombus) cells, confirmed both visually and via the exported cell-vertex counts (interior cells hold exactly 4 points; boundary cells clip to 3–5, the same expected pattern Hexagonal/Triangular/Diamond already show at their own edges); SVG export real closed `<polygon>` shapes matching the cell count exactly.

**`Distortion` (Off/Sine/Noise)** — the same separable-warp construction as Linear's own (below), generalised to Diagonal's non-orthogonal `u`/`v` basis: `realPoint(a, b) = center + (a + Da(b))·u + (b + Db(a))·v`, where `Da` depends only on the lattice's `b`-coordinate and `Db` only on `a` — a shared edge (constant `a` or constant `b` along its own length) is read identically by both of its neighbouring cells, same seamlessness guarantee, different (skewed) coordinate frame. **Verified**: Sine distortion renders a genuinely seamless organic rhombus-wave tiling — screenshot-confirmed no gaps or overlaps at the shared wavy boundaries between any two neighbouring cells, at both Skew 90 (rotated-square case) and sheared Skew values.

### Angular (`angular.js`) — geometric

Pure radiating sectors from a point, with NO ring subdivision — the direct sibling Radial's own header already implies but never builds. Each wedge is a straight-edged triangle from the centre out far enough to exceed the canvas in every direction, then Sutherland–Hodgman-clipped to the inner RECT (not a circle) — so wedges reach every edge and corner of the canvas, a genuine sunburst/fan filling the full rectangle, which Radial's own circular (or elliptical) boundary structurally cannot produce. `Center X`/`Center Y` (0–1, fraction of the inner rect) move the fan's own apex off-centre — at a corner this reads as a classic dazzle/op-art radiating composition instead of a centred sunburst.

**Verified**: default render reaches all four canvas corners with the apex centred, confirmed visually; SVG export real closed `<polygon>` triangles/quads (post-clip), one per sector, matching the cell count exactly.

**`Distortion` (Off/Sine/Noise)** bends each spoke's own ANGLE as a function of RADIUS — a twisting-fan/pinwheel wobble along the spoke's length. Every spoke index shares ONE distortion function of radius alone, so at Gap 0 two neighbouring wedges' shared edge collapses onto the identical nominal angle plus the identical distortion at every radius — coincident with no seam-matching special case, Angular's own version of the same separable-warp argument.

**A real aliasing bug, found live and fixed before shipping**: at the default Amount, spoke edges formed visible self-crossing loops (flower-petal artefacts). Root cause — the distortion's phase normalisation and its sample spacing both used `reach` (a deliberately huge value, sized to guarantee off-canvas clip coverage at any apex position/angle), so nearly all of Frequency's oscillation cycles fell in invisible off-canvas space, and the handful of `subdiv` points that DID land on-canvas were a severe undersample of the wobble anyone could actually see — classic aliasing, confirmed as the diagnosis (rather than an amplitude problem) because turning Amount down did not fix it. Fixed by computing a true `visibleRadius` (centre to the farthest canvas corner) and using it for BOTH the phase normalisation and dense sampling (`subdiv` raised to 24), with a single straight extension out to `reach` afterward purely for the off-canvas clip margin, where no one will ever see the difference. **Verified**: clean pinwheel at the default Amount (0.3) with no loops; clean tight vortex at an extreme setting (Amount 0.9, Frequency 6) with no self-intersection.

**Verified (Rectangular/Diagonal/Angular, together, plus Linear and Radial above)**: all render without error; SVG export for every one produces real closed per-cell shapes — verified by parsing the actual exported blob, not just eyeballing the preview; Rectangular's ratio-string round-trips correctly through Save grid/Load saved (saved "3,1,2,1", switched generators, reloaded — text field and resulting track proportions both restored exactly); 0 unaccessibly-named controls; zero console errors across every switch, drag, and export tested.

### Masonry (`masonry.js`) — geometric

Pinterest-style stacked columns: N equal-width columns, each independently filled with cells of randomised height (seeded, `Min height`/`Max height` as multiples of the column width) until the column reaches the canvas bottom — a structure no track-lattice generator can express, since row boundaries genuinely differ column to column (that's the entire point of masonry). Every cell is a plain axis-aligned rect, carried as a 4-point polygon rather than a col/row/span into a shared track list, since there is no shared row lattice on this axis for it to reference — the same trick Diagonal/Fractal/Recursive/Spiral all reuse rather than extending the JSON Model with a third cell representation just for this one shape. Each column's LAST cell is clamped to exactly fill whatever height remains, the same "no leftover unaccounted space" discipline `solveTracksParametric`'s own rescale step already applies elsewhere.

**`Distortion` (Off/Sine/Noise)** bends the vertical column SEAMS themselves — a genuinely different case from Linear/Diagonal/Angular/Radial's own 2D warps, since Masonry only ever has ONE family of shared boundaries (vertical seams between columns; row boundaries are never shared across columns by construction, the whole point of masonry). One `seamDx(y)` function of Y alone, shared by every seam index — the simplest possible instance of the separable-warp argument, since there's only one axis to keep separable in the first place. **Verified**: Sine distortion renders genuinely seamless wavy column boundaries — screenshot-confirmed the shared edge between any two adjacent columns traces the exact same curve from both sides, no gaps.

**Distortion rollout scope, decided per generator rather than applied uniformly**: extended from Linear (above) to Diagonal, Masonry, Angular, and Radial — every generator whose cell boundaries decompose into ONE OR TWO families of coordinate lines with a fixed nominal position along their own length (Diagonal's `a`/`b` lattice axes, Masonry's vertical seams, Angular's spoke angles, Radial's ring radii + spoke angles), which is exactly the property the separable-warp trick needs. **Fractal and Spiral were evaluated and explicitly deferred**, not silently skipped: both build cells through recursive/sequential SEQUENTIAL splitting, where a later split's own boundary can already be curved from an earlier one — "warp the sampled boundary line" isn't well-defined there the way it is for a fixed lattice, since there's no single shared coordinate a later cut's neighbours could read consistently. Making Distortion honest on either would need general polygon-edge splitting (subdividing and warping an already-curved boundary, not a straight nominal line), a materially bigger architectural change than every generator shipped this round — communicated to Diego rather than forced through. Hexagonal/Triangular/Diamond/Circular/Organic were not attempted either, for the same underlying reason as Fractal/Spiral's own deferral: those are non-orthogonal shared-EDGE tessellations (two cells meet along a whole shared edge, not along one of two fixed coordinate families), so the "one function of one coordinate, read identically by both neighbours" construction doesn't have an obvious generalisation there — a different, not-yet-designed technique, not a smaller version of the same one.

**Full regression across all 5 Distortion-capable generators, this round**: Linear/Diagonal/Angular/Masonry/Radial all confirmed rendering correctly (Diagonal and Masonry showed genuinely seamless wavy tiling on first try; Angular needed the aliasing fix above; Radial's apparent non-effect at the default Amount was resolved as a subtlety issue, not a bug, confirmed by both raw coordinate variance and a higher-Amount render); `Distortion: Off` verified an exact structural no-op on every one (`cell.smooth: false`, point counts back to the pre-Distortion baseline); zero console errors throughout.

### Fractal (`fractal.js`) — geometric

Recursive binary-space-partition subdivision with a `Split variance` wobble around 50/50 and `Depth` (leaves = 2^Depth). `Axis mode` (merged from what shipped as two separate generators, Fractal and Recursive — see the convergence table above) is the one real, load-bearing difference between them, now a single control instead of two registry entries: **Alternating** (Fractal's own original behaviour) strictly alternates the split axis with recursion depth (horizontal, vertical, horizontal, …), the same rule applied at every scale — the literal definition of self-similar, and genuinely capable of producing thin slivers at high depth on an already-narrow rect (a real, expected artefact of true alternation, not a bug). **Longest side** (the old Recursive generator's own behaviour) instead picks the axis by whichever side of the CURRENT rect is longer — a real treemap heuristic (the same family as squarified/slice-and-dice algorithms) that actively keeps leaves closer to square. Verified side by side at matched params: Alternating reads as a regular, repeating subdivision pattern; Longest side reads as a genuine treemap with varied, mostly-square block sizes — a real algorithmic difference, confirmed visually, not just in the code; both modes produce exactly 2^Depth leaves.

### Organic (`organic.js`) — geometric

Voronoi's relaxed sibling: identical half-plane-intersection cell construction, but after the first pass each seed is moved to its own cell's centroid and the whole tessellation rebuilt, `Iterations` times — Lloyd's algorithm, producing a centroidal Voronoi tessellation. Raw Voronoi's uniform-random seeding reliably produces some sliver cells next to normal ones; relaxation pulls every seed toward the middle of the region it already owns, converging toward more even, rounded, naturally-packed cells — verified visually as a clear, more hexagon-like regularity at Iterations 4 versus raw Voronoi's jagged polygons at the same seed. **Iterations 0 is an exact no-op**, verified by diffing: Organic's own cell list at Iterations 0 is byte-identical to Voronoi's own output at the same Points/Seed.

### Spiral (`spiral.js`) — geometric

The classic whirling-rectangle subdivision: cuts a strip off the current rect (`Ratio` of its relevant side), rotating direction 90° clockwise each time (right → down → left → up → right → …), `Count` cells total, the final leftover rect as the last cell. At `Ratio ≈ 0.382` (or its complement `0.618`) this IS the literal golden-rectangle/Fibonacci spiral construction — verified visually as the classic whirling-squares pattern. The built-in **"Golden Ratio"** preset (see below) is exactly this generator at that ratio on a canvas near the golden aspect ratio (1080×680) — not a separate generator, since the golden spiral is a specific parameterisation of this one, not a distinct topology.

## 5. Universal JSON Model (`js/json-model.js`)

```js
{
  version, generatedAt,
  canvas: { width, height, unit, orientation, margin, safeArea, bleed },
  grid: { type, solver, params, gap, padding, cellShape,
          tracks: { cols: [...], rows: [...] } },   // rect grids only
  cells: [ { id, col, row, colSpan, rowSpan } ]      // rect grids
      // OR [ { id, points: [[x,y],...], centroid: [x,y] } ]  — polygon grids (Voronoi)
}
```

`grid.cellShape` (`'rect'` or `'polygon'`) is the fork every renderer branches on. Rect grids deliberately do **not** store per-cell pixel `x/y/width/height` — those are always derivable from `tracks` + spans (`resolveCellRects`), and storing a derived value alongside its source is exactly how "which one is the truth" bugs happen. Polygon grids (Voronoi) have no track lattice at all — there's no meaningful "canonical span" representation for an arbitrary polygon, so their cells carry final absolute-coordinate points directly, resolved once at generation time. The CSS Grid renderer reads `tracks` + spans natively (`grid-template-columns`, `grid-column: n / span k`); SVG/raster/Figma read resolved pixel rects for rect grids, or `cell.points` directly for polygon grids — every renderer reads the same source either way, so none can drift from another.

**`cell.smooth` + `catmullRomPathD(points, r2)`** — a real bug fix, not a new feature: any Distortion-active polygon cell (Linear/Diagonal/Angular/Masonry/Radial) is built from densely-subdivided sample points along what's meant to read as one continuous curve, but every renderer originally drew those points as straight `L`-segment polylines (`<polygon>`/`lineTo` chains) — correct topologically, but visibly faceted rather than smooth, exactly the "looks like vector segments, not a single sinusoidal line" bug reported against Linear's own Sine export. Fixed once, at the model layer rather than per-renderer, so the three renderers and the live preview can't drift from each other: `catmullRomPathD` walks a closed point loop and emits a genuine `M ... C ... C ... Z` cubic-Bezier path, one curve threading exactly through every sample point (the standard Catmull-Rom-to-Bezier tangent conversion, `c1 = p1 + (p2-p0)/6`, `c2 = p2 - (p3-p1)/6`). Generators set `cell.smooth = true` only when they've actually subdivided a curve (i.e. only while Distortion is active) — every sharp-cornered generator (Hexagonal, Diamond, Triangular, Bento, …) never sets it, so `catmullRomPathD` is never applied where corners are meant to stay sharp. **Verified directly against the exported file, not just the live preview**: captured Linear's own real downloaded SVG (intercepting `Organica.download` rather than triggering an actual file save) and confirmed **0 straight `L` segments, 276 real `C` (cubic-Bezier) commands** across the file — the smoothing genuinely reaches the export, the same WYSIWYG guarantee every other Organica renderer already holds.

## 6. Renderers (`js/renderers/`)

- **`html-renderer.js`** — for rect grids, `paintGridDOM` paints the live preview as a *real* `display: grid` container (not absolutely-positioned divs simulating one); `buildHTMLSnippet` serialises the exact same CSS the DOM preview uses, so the on-screen canvas and the exported HTML file can never disagree — the same WYSIWYG rule as every raster/vector renderer elsewhere in Organica, applied to a DOM target instead of a `<canvas>`. For polygon grids (`cellShape === 'polygon'`), both functions branch to `buildPolygonSVG` instead — an embedded SVG preview, since CSS Grid has no honest way to represent an arbitrary polygon cell (§4's own Voronoi section has the full reasoning).
- **`svg-renderer.js`** — one CLOSED shape per cell (`<rect>` for rect grids, `<polygon>` for polygon grids), `fill="none"` by default but a real closed path a design tool can select and fill with a colour, plus a dashed margin guide. **Replaced a de-duplicated-edge-list version** (one `<line>` per unique boundary, never a closed per-cell shape) that Diego caught in real use: opening an exported file, nothing was actually a closed, fillable shape — just independent line segments that happened to line up on screen. The de-dup approach's own original motivation (avoiding a doubled-stroke look where two adjacent cells each draw their own copy of a shared edge) is accepted as a minor cosmetic trade-off now, since it's strictly less important than the shapes being closed and fillable at all. `json-model.js`'s own `collectEdges`/`collectPolygonEdges` were removed as dead code once nothing called them any more.
- **`raster-renderer.js`** — same fix, same reasoning: one closed shape per cell (`strokeRect` for rect grids, a real `beginPath`/`closePath`'d path for polygon grids) onto an offscreen `<canvas>` for PNG export, independent of SVG parsing.
- **Figma** — reuses `Organica.sendToFigma()` and the existing `figma-plugin/` verbatim: the grid arrives as vector guides via the plugin's existing SVG-import path. **Not yet** native Auto Layout frame generation — that's Phase 5 (§7). No UI button calls it currently — the Figma send button was removed product-wide across every Organica tool pending its return as a tab inside the Export popover; `sendToFigma()` stays defined, unwired, ready for that.

Export lives in the shared bottom-centre floating toolbar (`shared/organica-floatbar.css`), not the header — the same component Spore/Pollen/Halide/Komorebi/Living Path/Genesis Creator/Camo Turing all use; the header carries only the logo and status. Zoom/pan is the shared `Organica.createZoomPan` (`shared/organica-core.js`) on `#canvas-frame` — a pure CSS transform that never touches `canvas.width/height` or the JSON model, so no export can disagree with what's on screen regardless of zoom level. ## 7a. Phase 4 — WYSIWYG track editing, per-side margins, real Kiwi edit constraints

**Per-side margins.** `canvas-manager.js`'s `createCanvas`/`innerRect` took a single `marginPct` applied to all four sides (the MVP simplification disclosed in its own header). Now four independent fields — `marginTop`/`marginRight`/`marginBottom`/`marginLeft`, each still a percentage of the canvas's own shorter side, same convention as before. Panel gained a **Link margin sides** checkbox (checked by default — while linked, editing any one field copies its value to the other three; unchecked, each is fully independent) plus four fields laid out as a compact 2×2 grid, per Diego's own reference image — small pill boxes, each a direction glyph (a corner-bracket SVG icon) next to a plain number field, replacing four stacked full-width sliders. Reading order matches CSS's own clockwise-from-top shorthand mapped onto the grid's row-major order (top-left cell = Top, top-right = Right, bottom-left = Bottom, bottom-right = Left) — the glyphs are a compact visual identity for "four independent values" (the same idea as Figma's own corner-radius widget), not meant to encode the edge geometrically, since margin is a per-EDGE value, not a per-corner one. Backward compatible by construction, not by a migration pass: `loadGridPreset()` falls back to the old single `margin` field for any grid saved before this shipped (including every `BUILTIN_GRID_PRESETS` entry, none of which carry the new fields), same "legacy key stays readable" discipline every other Organica localStorage migration follows. `html-renderer.js`'s `buildGridCSS` needed a real fix alongside this, not just a pass-through: it computed one `marginPx` value and used it as a single CSS `padding: Npx`, which would have been silently wrong (only the top/left margin, applied to all four sides) the moment margins actually differed — now emits real per-edge `padding: top right bottom left`.

**Real Kiwi edit-constraint use.** `constraint-engine.js` gained `solveTracksKiwiWithEdit(count, innerSize, gap, minSize, editIndex, editValue)` — identical to `solveTracksKiwi`'s own setup (hard per-track minimum, hard sum-fills-canvas, medium-strength "want to equal track 0") plus one `addEditVariable`/`suggestValue` at `Strength.strong` on the dragged track. This is the exact mechanism `solveTracksKiwi`'s own header named as the point of choosing Kiwi in the first place, unused until now. Verified: the edited track lands within ~0.1px of the suggested value (strong dominates medium by ~1000:1 in Kiwi's own strength weights, not literally required, so a small solver-optimised deviation is expected and harmless); the canvas-fill sum stays exact before/after; a track pushed by the drag correctly hits the hard 16px floor when there isn't room. One honest note: the pre-existing equal-constraint topology is a *star* anchored at track 0 (`track[0] == track[i]` for every `i`, not a chain of adjacent-neighbour constraints) — dragging one boundary can visibly redistribute space to a **non-adjacent** track rather than only its immediate neighbour (reproduced and confirmed deliberate, not a bug: e.g. dragging column 0 left column 3, on the far side of the grid, also grew to match it, while the true neighbour hit its minimum). That's the documented "every other track re-solves automatically" behaviour working exactly as designed, just less locally-intuitive than a neighbour-only resize would be — flagged here rather than silently accepted, in case a future pass wants an adjacent-pair constraint topology instead.

**WYSIWYG drag-to-resize.** Scoped to the five `cellShape: 'rect'` generators only (Bento, Modular — Kiwi; Sinusoidal, Noise, Rectangular — parametric) — the fourteen polygon generators have no single linear boundary to grab (a Voronoi edge is shared unpredictably between neighbours, not a draggable line the way a track boundary is). `build()` now calls `renderTrackHandles()`, which places a thin (9px hit-zone) absolutely-positioned handle over every internal track boundary in `#track-handles` (a new layer above `#grid-preview`, cursor `col-resize`/`row-resize`), positioned from the exact same `offsets()` helper `resolveCellRects` already used internally — now exported from `json-model.js` rather than kept private, specifically so the handle positions can never drift from where the boundaries actually render. Dragging mutates `currentModel.grid.tracks` directly and repaints (`paintGridDOM` + `renderTrackHandles`, re-reading the current `zoomPan.zoom` to convert screen-pixel drag distance into canvas-space) — it deliberately never calls `build()`, which would regenerate from params/seed and throw the edit away; cell topology (col/row/span) is untouched, since a track-size edit never changes which cell owns which span. Kiwi-solved generators re-solve via `solveTracksKiwiWithEdit` above; parametric generators (no live solver instance) get the dragged track set directly with every other track rescaled proportionally so the sum still fills the canvas exactly — the same normalise-then-rescale discipline `solveTracksParametric` already applies, just run from a fixed point instead of a fixed ratio.

A dragged layout is a real, persistent part of the model, not a transient preview-only state: every export (PNG/SVG/HTML/JSON) already reads `currentModel` as-is, so a drag exports correctly with zero extra plumbing — verified directly (SVG export after a drag still produces the exact right closed-`<rect>` count). **Save grid initially did NOT capture it** — caught by testing the round-trip, not assumed: `loadGridPreset()` calls `build()` to restore the generator's own params, which correctly regenerates fresh EQUAL tracks and silently discarded whatever the drag had done, the same way it already resets Shuffle Numbers. That's right for every other control but wrong for a WYSIWYG edit, which is the entire point of the feature — fixed by restoring the saved model's own `grid.tracks` over the freshly-built ones immediately after `build()` (track counts always match, since the same params just regenerated them, so no length-guard is needed). Verified end to end: drag a Bento column, Save grid, switch to a different generator entirely, Load saved — the exact dragged track values come back, confirmed by diffing the arrays, not just eyeballing the render. A full rebuild (any other panel control changing) still correctly discards an in-progress drag, same "resets on next real change" semantic as Shuffle Numbers.

Discovered and fixed one bug along the way, from testing rather than from reading the diff: the drag-handle visibility check (`cellShape !== 'rect'`) was backwards — no rect-lattice generator ever sets `cellShape: 'rect'` explicitly (only polygon generators set their own flag; every existing check elsewhere in this codebase, `paintGridDOM` included, tests for `=== 'polygon'` instead), so the check as first written hid handles on every single rect generator, the opposite of the intended behaviour. Caught immediately by testing Bento live (0 handles rendered) rather than assuming the code was correct because it looked reasonable.

**Verified**: per-side margins render a visibly asymmetric canvas correctly (Top 15 vs. Right/Bottom/Left 10, confirmed both visually and via the resolved inner-rect math); Link toggle confirmed both linked (all four move together) and unlinked (fully independent) live; all 5 rect-lattice generators show the correct handle count (Bento 6, Sinusoidal/Noise 11, Modular 10, Rectangular 4, for their respective default track counts) and every polygon generator shows 0; Kiwi-mode and parametric-mode drags both preserve the exact canvas-fill sum before/after; Save/Load round-trip preserves an exact dragged layout; all 21 generators + 5 built-in presets regression-clean together, 0 of 125 panel controls unaccessibly-named, zero console errors.

## 7d. Overlay grid — comparing two grids on one canvas

Asked to evaluate a general multi-grid layered system first (arbitrary N layers, blend modes, reorderable stack) — flagged as a real Phase-7-sized rebuild (new Model schema every renderer including live CSS Grid would need to branch on, a real layer-stack UI), not a small add-on, and NOT built. Diego's actual goal was narrower: overlay exactly TWO grid definitions, simply, for visual comparison/alignment. Rescoped down and shipped as that, once a follow-up question ("perché l'export è complesso? se le grid si combinano in uno layer nell'export?") corrected an overstated claim — combining two grids' shapes into ONE flat output file is plain concatenation (draw both, in sequence, into the same document), not real N-layer compositing (blend modes, opacity affecting a shared schema); the genuinely hard part only applies to the general case, not this one.

**What it is**: a second saved grid, picked from the SAME preset list Save/Load already use (`allGridPresets()` — no separate store), regenerated via its own `grid.type`/`grid.params` against the CURRENT canvas's inner rect (deliberately the opposite choice from Load saved grid, which adopts the preset's own saved canvas size — Overlay always fits Layer A's canvas, regardless of what canvas the preset was originally saved on), drawn on top in a distinct colour (`--overlay-orange`, `#ff6b35` — same "content colour, not UI chrome" exception as `--guide-blue`) at an adjustable Opacity. Zero Model schema changes: `svg-renderer.js`/`raster-renderer.js` each gained one small reusable export (`cellsMarkup`/`drawCells` — just the cell-shapes-only piece their own full-document renderer already built, extracted so a second call can inject a second grid's shapes without a second opaque background wiping out the first) and `main.js` calls the generator function a second time. Live preview: a second absolute-positioned `#overlay-frame` div (z-index 3, between `#grid-preview`'s 2 and `#track-handles`' 4, non-interactive) holds an embedded SVG built from `cellsMarkup`. Export: `exportSVG()` splices `cellsMarkup`'s markup (wrapped in `<g opacity="...">`) in before `</svg>`; `exportPNG()` calls `drawCells` a second time on the SAME canvas context `renderRaster` already produced (the transform/scale set up by the first call persists, so the overlay draws at the correct physical scale for free) under `ctx.globalAlpha` matching the Opacity slider. HTML export stays Layer-A-only — its CSS-Grid path has no absolute-overlay slot the way `#canvas-frame` does, not attempted this round.

**A real pre-existing bug found and fixed along the way, not introduced by this feature**: Bento/Masonry/Rectangular/Wave's own `generate()` destructures `gap` OUT of `params` before echoing the rest back as the returned `grid.params` (storing it once, at the top-level `grid.gap`, instead) — every other generator keeps `gap` inside its own `params` object. Feeding a saved preset's bare `grid.params` straight back into `generate()` (which Overlay's own `buildOverlayModel()` does, and which `loadGridPreset()` was ALREADY doing via `applyGridParamsToUI(model.grid.type, model.grid.params)`) silently drops Gap for exactly those four generators — `solveTracksKiwi`/`solveTracksParametric` then received `gap: undefined`. For Overlay this threw inside the try/catch and the overlay simply never appeared, no visible error (reproduced live: `sel-overlay-grid` correctly read "Base Bento", `buildOverlayModel()` correctly returned `null`). For Load saved grid it's quieter but real: the Gap slider silently failed to restore to its saved value for those same four generator types, falling back to whatever it already read. Fixed once, at the source, with a small shared `paramsWithGap(grid)` helper (`{ ...grid.params, gap: grid.gap }` when params doesn't already carry it) used by both `buildOverlayModel()` and `loadGridPreset()`'s own call — not two separate patches. **Verified the fix actually fixes the bug, not just that a plausible-looking value appears**: saved a Bento preset at a NON-default Gap (25, versus the HTML default of 12 — the first check used the coincidentally-matching default and would have passed even with the bug still present, caught before treating it as confirmation), changed Gap away, reloaded the preset, confirmed the slider read back 25.

**Verified**: overlay renders visibly distinct orange lines over a differently-shaped base grid (Bento over Hexagonal, screenshot-confirmed); exported SVG contains the real `#ff6b35` overlay group (parsed from the actual downloaded blob, not the live preview); exported PNG contains real orange-tinted pixels (33,014 sampled, confirmed via `getImageData` on the decoded blob, not assumed from file-size alone); switching Overlay back to "None" clears `#overlay-frame` and removes it from both exports; deleting the underlying saved preset while it's the active overlay selection doesn't throw; 0 of the 2 new controls unaccessibly-named; all 15 generators regression-clean; zero console errors throughout.
