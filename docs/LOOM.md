# Loom — Universal Grid Generator — manual

`/loom/` — a universal layout-grid engine: every grid is generated from a common mathematical model, resolved once into a Universal JSON Model, then rendered by independent renderers (live HTML/CSS Grid, SVG, PNG, and — via the existing shared Figma pipeline — a Figma import). Not a column generator: the brief this was built from (`Grid Definition`, Notion) is explicit that this is a constraint-driven, multi-generator system meant to become an industry-standard layout tool.

**Status: Phase 1 (MVP) + four Phase 2 generators + two Phase 3 presets.** Two MVP generators (Bento, Sinusoidal — the brief's own "one simple, one complex" pairing to prove the architecture end to end) plus Voronoi, Hexagonal, Radial, Triangular, Diamond and Circular (six `cellShape: 'polygon'` generators, each a real structural variant — tessellation-of-arbitrary-cells, tessellation-of-one-repeated-hexagon, true polar coordinates, tessellation-of-one-repeated-triangle, tessellation-of-one-repeated-square, circle-packing), the full pipeline below, and a Figma export that reuses the existing SVG-import plugin as-is. The remaining ~18 elementary/preset grid types, WYSIWYG cell editing, and native Figma Auto Layout frame generation are later phases — see §7.

## 1. Architecture

```
Canvas Manager (physical space: size, unit, margin, safe area, bleed)
     ↓
Grid Definition Engine (generator registry — js/generators/registry.js)
     ↓
Constraint Engine (per-generator: Kiwi solver OR direct parametric math)
     ↓
Universal JSON Model (js/json-model.js)  ← single source of truth
     ↓
Renderers: live CSS Grid · SVG · raster PNG · Figma (via shared pipeline)
```

Native ES modules (`loom/js/*.js`, `import`/`export`, no bundler) — the one deliberate deviation from every other Organica tool's single-file convention, chosen because this engine has a real module boundary (canvas → generators → solvers → model → renderers) that a 3000-line single file would obscure rather than simplify. `kiwi` and `Organica` are both classic global scripts loaded before the module entry point, read as unqualified globals inside the modules — same load-order pattern Camo Turing already uses for `Organica` inside its own `<script type="module">`.

## 2. The Kiwi / parametric split — the central architecture decision

Two solvers, chosen **per generator**, not globally — this was the explicit output of an architecture discussion before any code was written (the brief's own instruction: "Always explain architectural decisions before writing code").

- **Kiwi** (`shared/kiwi.min.js`, vendored — MIT/BSD-3-Clause, no CDN, same convention as Paper.js in Strata) — a real Cassowary constraint solver. Used where tracks should size **equally by default but be overridable under priority** — Bento today; every future modular/column/row grid, and Phase 4's WYSIWYG drag-to-resize, where dragging one track becomes a stronger edit constraint and the rest re-solve automatically, with no hand-written redistribution logic.
- **Parametric** (`js/constraint-engine.js`'s `solveTracksParametric`) — direct closed-form math, no solver. Used where tracks follow a continuous function that isn't a linear constraint — Sinusoidal today; every future radial/polar/noise generator.

`js/constraint-engine.js` exposes both; each generator picks the one that actually matches its own behaviour, documented in its own file rather than hidden behind a generic dispatcher.

## 3. Canvas Manager (`js/canvas-manager.js`)

Width/height/unit (px, mm, cm, or m), a preset library (`Square 1:1`, `Landscape 16:9`, `Portrait 4:5`, `Widescreen 3:2`, `A4 portrait/landscape`, `Letter portrait`), Margin and Safe area (both a single percentage of the canvas's own shorter side, applied to all four sides), and Bleed (always mm regardless of canvas unit — the real print convention — shown for any non-px unit).

**Units — px vs. the metric family.** mm/cm/m convert between each other with clean decimal factors (`UNIT_TO_MM = { mm: 1, cm: 10, m: 1000 }`); px does not — a CSS pixel has no fixed physical size, so "converting" it to mm would mean silently assuming a DPI nobody asked for. `createCanvas` canonicalises any mm/cm/m input to an internal **mm-equivalent** number (`canvas.width`/`canvas.height`) that every generator, `innerRect`/`safeAreaRect`, and the on-screen canvas-frame sizing read directly — none of them need to know or care which of the three the user actually typed. `canvas.displayWidth`/`displayHeight`/`unit` keep the raw typed number, unconverted, purely for showing it back to the user. Gap and Padding (absolute-number sliders, unlike the percentage-based Margin/Safe area) go through the same canonicalisation (`main.js`'s `unitVal()`) — and their own slider range/step rescales when the unit changes (`UNIT_RANGES`, `rescaleUnitField`), converting the CURRENT value to preserve its physical size rather than leaving the raw number unchanged and silently meaning something else (a Gap of "12" is 12mm under `mm` but would be 12 *metres* under `m` with no rescale — verified live that switching units keeps the physical gap constant, e.g. 12mm → 1.2cm → 0.02m, the last step-snapped by the `m` slider's own 0.02 granularity).

**Export unit suffixes.** SVG's and CSS's `width`/`height` need a real unit suffix on a physical canvas or the bare number is read as px — a genuine bug found while building this (an A4 canvas exported `width="210"`, i.e. 210px, not 210mm; the manual's own earlier claim that this already worked was wrong). Neither SVG nor CSS has a native **metre** unit, so any non-px unit — mm, cm, *and* m — exports as a literal `mm` suffix using the already-canonical mm-equivalent number (e.g. a 3m canvas exports `width="3000mm"`, dimensionally exact). `viewBox` and the grid's own internal CSS (`grid-template-columns`, `gap`, `padding`) stay bare canonical numbers rendered as px, matching the existing on-screen convention — only the outermost declared width/height carries physical meaning.

**Disclosed simplification**: per-side margins are a real brief requirement but deferred to the WYSIWYG-editing phase, since a per-side value wants a visual drag handle, not four more blind sliders. Safe area is a guide only in this phase — it doesn't clip generator output. On-screen preview treats 1 canonical unit as 1px regardless of the declared physical unit (no device-DPI-aware physical preview exists anywhere in Organica yet) — the exported file is always dimensionally correct even though the on-screen preview isn't physically true-to-size.

**Three canvas verification toggles** (`syncCanvasOverlays()` in `main.js`), all pure `#canvas-frame` CSS state, none of them touch the model and none are ever baked into an export (verified directly: exporting with all three on still produces `fill="none"` shapes and zero `repeating-linear-gradient` artefacts — the toggles are display-only, generated purely by the browser, not present in the model at all): **Background grid** — a translucent reference reticle, 12 divisions across the canvas's own width (density derived from the canvas, not hardcoded), drawn *above* the grid content rather than behind it — the initial version placed it behind and it was invisible, since every renderer's own opaque white background rect (needed for a standalone exported file) fully blocked anything underneath; fixed the same way a light-table guide layer sits above content in Photoshop/Illustrator. **Preview fill** — tints every cell with a faint colour, a direct visual proof that each cell is a real closed, fillable shape (the thing the SVG/PNG/HTML export fix above exists for) — implemented as one CSS rule overriding the polygon/rect `fill="none"` presentation attribute (CSS wins over SVG presentation attributes) plus the equivalent `background-color` for the CSS-Grid rect-cell path, so no renderer code needed to change. **Show numbers** — hides the number labels via CSS on both preview paths (`.loom-cell` text colour, SVG `<text>` display) rather than changing `main.js`'s own number-assignment logic, since hiding is a display concern, not a data one. Cell number font size raised from 9px/10px to 13px on both preview paths (CSS `.loom-cell`, SVG `<text>`) at the same request.

**Save grid — named presets + cross-tool import.** The brief's own stated workflow: define a canvas + grid in Loom, save it, then reuse that exact grid in any other Organica tool (or Figma/Affinity). Two pieces:

- **`Organica.presetStore('loom')`** (Save grid panel section) — the same shared named-preset store every other Organica tool already uses (`organica.loom.presets`), storing the FULL model (`buildModel()`'s own output — canvas, grid, cells), not a re-derivable subset. **Load** is a real round-trip, not just a re-display: `applyGridParamsToUI(type, params)` is the mirror image of `readGridParams()`'s own explicit per-generator branches (deliberately explicit rather than a naming-convention guesser — the same reasoning `readGridParams` already follows, since a few param names don't match their control IDs directly: Sinusoidal's `amplitude`/`frequency` → `rg-sin-amp`/`rg-sin-freq`, Radial's `innerRadiusFrac`/`startAngle` → `rg-radial-innerradius`/`rg-radial-startangle`). **Verified**: saved a Hexagonal grid (Rotation 30°, Spin mode Noise), switched to Bento, loaded the saved preset back — every control (including the two conditional Spin rows) re-synced to its exact saved value and the render matched pixel-for-pixel.

- **`Organica.loadLoomGrid(json)`** (`shared/organica-core.js`) — the cross-tool half: reads Loom's own JSON export (parsed or a raw string) and resolves it into absolute per-cell geometry — `{x,y,width,height}` rects for `cellShape:'rect'` grids, `{points,centroid}` polygons for `cellShape:'polygon'` grids — that any OTHER Organica tool can consume without knowing anything about tracks, spans, Kiwi, or Loom's own generator internals. Deliberately NOT an ES-module import of Loom's own `json-model.js` (ports the two small pure functions it needs — `innerRect`, `resolveCellRects` — instead): every other Organica tool is a plain single-file `<script>` with no bundler, the same reason every polygon generator in `loom/js/` already keeps its own private copy of `clipToRect` rather than sharing one. Throws a plain, user-safe `Error` (not a stack trace) on invalid JSON or a non-Loom object, matching the "never let a bad file import crash the host tool" discipline every file-input handler elsewhere in Organica already follows. **Verified**: real exports from both a rect-cellShape grid (Bento, 10 cells) and a polygon-cellShape grid (Hexagonal, 67 cells) round-tripped through `loadLoomGrid` correctly; a malformed-JSON input threw the expected clean error message rather than crashing.

- **Both cross-tool behaviours the brief names are now concept-proven**, neither shipped into a host tool yet — two standalone test pages, not linked from the hub:
  - **Slice & Reposition** (`loom/_test-slice-reposition.html`) — the tool-agnostic one: export a real grid from Loom, load it via `Organica.loadLoomGrid` in a separate page, and use its resolved cell geometry to slice+reposition an external image (a "puzzle remix": each cell samples a corresponding — optionally shuffled — fractional region of a source image and redraws it into that cell's own clipped shape). Verified on both rect and polygon cellShapes, faithful-slice and shuffled modes alike.
  - **Mix & Restructure** (`loom/_test-mix-restructure.html`) — the deeper, per-tool-integration one: each cell runs its OWN independent generative pass, not a shared crop. Ported Spore's real placement algorithm (`spore/index.html`'s `doRender()` — a hex-jittered lattice, mark size driven by local image darkness, points below `luma > 0.92` skipped) faithfully for the lattice/sizing math, simplified the mark itself to plain circles rather than replaying a full Genesis SVG symbol (disclosed, not hidden — that needs `organic-forms.js`'s mark data, a bigger dependency than a concept test needs). Each cell independently samples its own sub-region of one shared source image and runs its own stippling pass with its own spacing/size/rotation — cycled through a small fixed preset list by cell index (reproducible, not random-every-render) rather than truly random, so results can be verified. Verified live on both a 3×3 Bento grid (9 cells) and a Hexagonal grid (45 cells): "Vary structure per cell" shows genuinely distinct textures per container while still faithfully tracking the source image's own luminance; "uniform structure" (identical spacing/size/rotation everywhere) reads as one continuous pattern only interrupted by the clip shape, the correct baseline contrast — proves a grid cell can be a real independent generative container, the concept this whole thread of work set out to test, not just a crop window with a fancy border.

  Both prototypes share the same architecture: `Organica.loadLoomGrid` for the grid, an offscreen canvas per cell for the corresponding source-image sub-region, `ctx.clip()` to the cell's own shape (rect or polygon) before drawing. Zero console errors on either, across every generator/mode combination tested.

## 4. Generators (`js/generators/`)

### Bento (`bento.js`) — Kiwi

A base Columns×Rows lattice where adjacent cells are randomly merged (seeded) into 1×1 up to 2×2 rectangular spans — the mixed-size look a Bento grid is named for. `Variety` gates how often a merge is attempted; **0 is a verified exact no-op** (a plain uniform grid, every cell 1×1). Track sizing is solved by Kiwi: every column/row equal by default (medium-strength constraint — a soft preference), a hard minimum size, and a hard "tracks + gaps fill the canvas" sum.

A first version weighted each track by how many spans touched it, meant to make a track under a wide cell size up proportionally — reverted after testing, because dividing a wide cell's contribution across its own tracks made them *thinner*, the opposite of the intended effect. Bento's visual variety comes entirely from the span topology, not from unequal track sizing.

### Sinusoidal (`sinusoidal.js`) — parametric

A full Columns×Rows lattice, no merged spans — the rhythm here is in **track size**, not topology. Each column width (or row height, or both — `Axis`) follows `1 + Amplitude · sin(t · Frequency · 2π + Phase)` as a relative weight, then rescaled to fill the canvas exactly (`solveTracksParametric`'s normalise-then-rescale, the same shape Warping's own pattern functions use).

**Honesty note** (same discipline as Camouflage's "Stripes/worms" disclosure): this modulates track *size*, not track *boundary shape*. A literal wavy grid line isn't representable in real CSS Grid (`grid-template-columns` is a list of straight sizes) or as an axis-aligned SVG rect grid, so "sinusoidal" here means a rhythmic width/height sequence — honestly renderable by every promised target, rather than a wavy-edged grid the CSS renderer could never actually deliver.

### Voronoi (`voronoi.js`) — geometric

The first **polygon-shaped** generator, not a rect one — a real architecture fork, not a Bento variant. `N` seed points scatter (seeded) inside the inner rect; each cell is that seed's own Voronoi region, built by half-plane intersection: start from the inner rect as a polygon, then for every OTHER seed clip to the half-plane on this seed's own side of their perpendicular bisector (Sutherland–Hodgman), repeated over all seeds. O(N²), trivial at the cell counts this tool uses (a handful to a few dozen), and far simpler to get right than Fortune's algorithm for the identical result. `grid.cellShape = 'polygon'` and `grid.solver = 'geometric'` — genuinely a third category, neither Kiwi nor the parametric track math, since there's no track lattice and no linear constraint system at all.

**Why there's no CSS Grid form**: Voronoi cells are arbitrary convex polygons: there is no honest way to fit them onto CSS Grid's own track lattice (a bounding-box approximation would be a fake, the exact kind of degenerate output this project's conventions refuse elsewhere — see the Padding no-op discipline, or the real-vector-SVG rule shared across every Organica tool). So `main.js`/`html-renderer.js` branch on `cellShape`: rect grids get the live CSS Grid preview described above; Voronoi's preview is an embedded SVG instead (`buildPolygonSVG`), drawing each cell as its own closed `<polygon>` (see §6's own note on the closed-shape fix), so preview and export are about as close to byte-identical as this tool gets. The one deliberate difference: the preview also draws each cell's number at its polygon centroid — numbers were always a preview/HTML-snippet-only feature for rect grids too (the SVG *export* has never drawn them), so Voronoi just keeps that existing convention rather than inventing a new one. Gap and Padding don't apply to polygon cells yet (no defined "shrink a polygon inward" operation shipped) — hidden from the panel rather than left as dead controls, per the same rule Komorebi's own control audit established (`docs/KOMOREBI.md` §18).

### Hexagonal (`hexagonal.js`) — geometric

The second polygon-shaped generator, and proof the `cellShape: 'polygon'` fork Voronoi introduced generalises for free: this file only had to produce cells shaped `{ points, centroid }` — every renderer (SVG/PNG export, the embedded-SVG live preview) already branches on the flag, so nothing outside `hexagonal.js`/`registry.js`/the panel block changed to add it.

Real regular-hexagon tessellation (the standard redblobgames flat-top axial-spacing formulas — `1.5r` horizontal / `√3·r` vertical, odd columns offset by half a row), not a distorted hex-ish shape. `Columns` sets the target horizontal spacing (`inner.width / cols`), from which the hexagon radius and both spacings are derived — density, not a literal hex count, so the same slider value behaves consistently on a square canvas or a wide banner. `Gap` shrinks each hexagon toward its own centre before clipping (the polygon analogue of rect-cell Padding, applied pre-clip since a polygon has no separate track size to shrink into) — **verified 0 is an exact no-op**: edge-to-edge tessellation, single de-duplicated boundary line, no doubled-stroke artefact. `Jitter` offsets each hexagon's centre by a seeded random amount before the polygon is built, breaking the lattice into an organic hand-set-tile look (verified visually: overlapping, unevenly-spaced hexagons at Jitter 0.7, vs. a perfect grid at 0).

**`Rotation` (0–60°), not a Flat-top/Pointy-top toggle.** The original ship used a two-way segmented control; replaced same-session per Diego's own request for a continuous control, since the toggle's two options were never really a binary — "pointy-top" IS "flat-top" rotated 30°, and a rigid hexagonal tiling tiles at *any* angle, not just those two. The naive version of this — rotate each hexagon's own SHAPE while leaving the lattice centres fixed — is wrong: a hexagon's edges only meet its neighbours' edges when the shape's orientation matches the lattice's, so a shape-only rotation opens visible gaps/overlaps at any angle that isn't a multiple of 60°. The fix is to rotate the CENTRES and the SHAPE together, a rigid rotation of the whole pattern, which the honeycomb's own rotational symmetry guarantees still tiles at every angle. Implementation: the lattice is built in its own unrotated frame first (sized from the inner rect's own diagonal, not its width/height, so a rotated lattice still covers every corner of the actual — unrotated — inner rect), rotated as a whole around the inner rect's centre, then clipped against the real axis-aligned inner rect. The control's range is exactly `[0, 60)` because that's the hexagon's true rotational period (0 = the old "Flat-top", 30 = the old "Pointy-top") — anything past 60° just repeats. **Verified**: 0° and 30° reproduce the old two named orientations pixel-for-pixel; an in-between angle (15°) tiles the whole canvas edge-to-edge with zero gaps/overlaps, confirmed visually and via a real de-duplicated SVG export (220 `<line>`s on a 73-cell canvas); Gap 0 stays an exact no-op at every rotation tested.

**`Spin mode` / `Spin amount` — per-CELL rotation, a deliberately different control from `Rotation`, not a finer-grained version of it.** Diego's own follow-up: "what if we rotate each individual hexagon?" `Rotation` rotates centres and shapes *together* (rigid, tiling-preserving, above); Spin rotates only each hexagon's own local orientation on top of that — which by definition can't preserve edge-to-edge tiling once neighbours stop facing the same way, the same honest trade-off `Jitter` already makes for position. Since "rotate each hexagon" doesn't name one specific effect, structurally different generators of the idea were built across two rounds (asked, not guessed, since they don't converge visually the way colour presets do) and exposed as a `Spin mode` dropdown (Off/Random/Checkerboard/Radial/Spiral/Noise — a dropdown rather than a segmented control, since word labels don't fit more than ~3 short options in a 248px panel without truncating, caught live before shipping): **Random** — seeded, uniform in `[-Amount, +Amount]` per cell, a fractured hand-set-mosaic look. **Checkerboard** — alternates `±Amount` by `(col+row)` parity in the lattice's own unrotated indices, a deterministic woven pattern, not random. **Radial** — `Amount` scaled by each cell's distance from the inner rect's centre (0 at centre, full `Amount` at the corners), a continuous "unfurling" gradient. **Spiral** — `Amount` scaled by each cell's *angle* around the centre (`atan2`, not distance), a true pinwheel/vortex twist; angle wraps at ±π so there's a real, intentional seam where Spin jumps from `-Amount` to `+Amount` — disclosed rather than smoothed away (smoothing it would make it a wave, a different mode). **Noise** — `Amount` scaled by a seeded 4-octave value-noise field (`Organica.noise.fbm`, `shared/organica-noise.js` — Loom's first consumer of the shared noise module, ported rather than a fourth private copy after Komorebi/Camo Turing/Warping) sampled at each cell's centre, an organic wind-blown texture; the one mode with its own second control, `Noise scale` (cycles of the field across the canvas), since "how chaotic" and "how big are the swirled regions" are independent knobs. Applied to each hexagon's own local vertex angles *before* the rigid `Rotation` step, so Spin composes correctly with Rotation instead of fighting it. `Off` (default) is an exact no-op — Spin Amount is hidden whenever Off is selected, `Noise scale` shown only for Noise, same dead-control-avoidance rule as Voronoi/Bento's own conditional rows.

**Two real bugs found during verification of this round, both fixed, neither caused by the geometry itself:** (1) `window.syncHexSpinRow` was never exported in `main.js`'s own window-export block, so the Spin mode dropdown's inline `onchange` handler threw on every real switch — invisible in an earlier verification pass only because that pass checked a fresh tab's console *without* actually exercising a mode switch in it (a proxy check, not the real one); fixed by adding the missing `window.syncHexSpinRow = syncHexSpinRow` line, then re-verified by switching through all 6 modes in one pass with a clean console throughout. (2) Independent of Spin entirely: a *fresh Loom load* — plain default Bento, zero interaction — was landing at 1% zoom, fully off-screen, because `fitToViewIfNeeded`'s very first call (synchronous, at module init) could read `canvas-wrap`'s `clientWidth` before its own layout had settled, went negative once the 64px margin was subtracted, and that negative "available space" fed a negative scale into `zoomBy` which the zoom-pan module's own floor clamps to 1%. Fixed by retrying on the next animation frame (without committing `lastFitKey`) whenever the measured available space isn't yet positive, instead of fitting to garbage dimensions — verified a fresh load now lands at a sane fit (57% in the tested viewport) with no manual reset needed.

**Verified**: Off reproduces the pre-Spin render pixel-for-pixel; all five active modes render as visually distinct (Random = fractured, Checkerboard = regular alternation, Radial = smooth centre-to-edge gradient, Spiral = pinwheel with an honest seam, Noise = organic spatially-coherent wobble); SVG export still real vector geometry in every mode (384–388 `<line>`s on a 67-cell canvas, mostly no-longer-deduped, correctly, since neighbouring edges stop aligning once spun); 0 of the block's controls unaccessibly-named; all four generators × all six Spin modes regression-clean, zero console errors confirmed by actually exercising every mode switch, not just loading the page.

**Diego caught a real dead-control gap by asking to check Seed specifically, later the same day**: with Jitter 0 and Spin mode Noise, changing Seed had zero effect — `Organica.noise.fbm` has no seed parameter at all, so unlike Random (genuinely seeded) or Checkerboard/Radial/Spiral (genuinely deterministic by design, correctly seed-independent), Noise's insensitivity to Seed was neither. Fixed by sampling `fbm` at a per-generation `(x,y)` offset drawn from a SECOND, independent `mulberry32` stream (seeded from a distinct transform of `seed`, `seed ^ 0x9E3779B9`) — deliberately never sharing draws with the main `rng` that feeds Jitter/Random, so the fix couldn't perturb either of those at a fixed seed. Ported identically to Triangular and Diamond, since all three share the exact copied `spinFor`. **Verified**: Noise now genuinely differs across Seed values on all three generators (confirmed by diffing the exported JSON model, not just eyeballing it); Random's own seed-dependence unaffected on all three; all seven generators regression-clean, zero console errors.

Clipping reuses the same Sutherland–Hodgman technique as Voronoi's own `clipHalfPlane`, generalised from one half-plane per neighbour seed to 4 fixed half-planes (the inner rect's own edges) — a hexagon straddling the inner-rect boundary is trimmed to a real partial polygon, not dropped or left overflowing. Verified end to end: both orientations render correctly, Gap/Jitter/Columns/Seed all rebuild live, SVG export contains real de-duplicated polygon-edge geometry (276 `<line>` segments on a 95-cell canvas, not a degenerate fallback), all four generators (Bento/Sinusoidal/Voronoi/Hexagonal) regression-tested together with zero console errors, 0 of the block's controls unaccessibly-named (the two orientation segmented buttons carry their own visible text, same convention as every other `seg-ctrl` in Loom).

### Radial (`radial.js`) — geometric

The third polygon-shaped generator, and a genuinely different STRUCTURE from both families before it, not another variation of an existing one — Bento/Sinusoidal are a Columns×Rows track lattice, Voronoi/Hexagonal are a tessellation of one repeated cell shape; Radial is real polar coordinates, concentric Rings crossed with angular Sectors, each cell a curved ring-sector wedge — the dartboard/sunburst/mandala structure neither of the other two families can honestly produce. `cellShape = 'polygon'` again, but each cell's two curved edges are approximated as short line segments (roughly one vertex per 10° of arc) rather than the 3–6 straight edges every other polygon generator emits — a real arc has no exact polygon form, so it's subdivided finely enough to read as smoothly curved at any reasonable Rings × Sectors count.

**No inner-rect clipping needed**, unlike Voronoi/Hexagonal — genuinely simpler, not a shortcut: the whole radial field is built inside a circle already inscribed within the inner rect (`outerRadius = min(inner.width, inner.height) / 2`), so every wedge is guaranteed to land fully inside it by construction. `Inner radius` (0–0.8, fraction of the outer radius) is the dartboard/donut-chart control — 0 gives true pie-slice wedges at the innermost ring, the "inner arc" degenerating to a single point at the centre through the *same* arc-point code (not a special case): every point on a near-zero-radius arc just lands at the centre, drawing as a zero-length segment for free. `Gap` insets each wedge inward on both its radial and angular sides before the arc is built — the same "shrink toward the cell's own middle" idea as Hexagonal's own Gap, with two independent inset amounts since a wedge has two genuinely different kinds of edge. `Start angle` rotates the whole field. At Gap 0 this tiles edge-to-edge exactly (concentric circles + radial spokes, single de-duplicated lines throughout), the same "0 = true no-op" discipline as every other Organica control.

**Verified**: Inner radius 0 renders true converging pie slices at the centre with no glitch; Gap 0 is an exact edge-to-edge no-op; Start angle rotates the whole field correctly; both extremes tested without error (1 ring × 3 sectors = 3 cells; 12 rings × 36 sectors = 432 cells); SVG export real de-duplicated vector geometry (213 `<line>`s on a 48-cell canvas); 0 of the block's controls unaccessibly-named; all five generators (Bento/Sinusoidal/Voronoi/Hexagonal/Radial) regression-clean with the console actually watched through every mode switch, not just page load — the exact discipline the previous Hexagonal-Spin round learned the hard way.

### Triangular (`triangular.js`) — geometric

The fourth polygon-shaped generator — real equilateral-triangle tessellation (alternating up/down triangles via the standard `h = side · √3⁄2` row-height construction), not a rectangle-cut-in-half approximation, which only tiles at 90°/45° and reads as a cut rectangle rather than a triangular mesh. `Columns` sets the target triangle side length (`inner.width / cols`), matching Hexagonal's own density-not-count convention. **Genuinely does need inner-rect clipping**, unlike Radial and unlike this file's own first-draft doc comment claimed before being corrected during the same build — Radial's field is inherently bounded by its own outer radius by construction, but a plain triangle row/column loop has no such built-in boundary, so boundary triangles are trimmed with the same Sutherland–Hodgman `clipToRect` Hexagonal already uses (each polygon generator keeps its own private copy rather than sharing one, the established pattern in this file set). `Gap` shrinks each triangle toward its own centroid (same idea as Hexagonal's own Gap); `Jitter` offsets each triangle independently before the shrink, the same accepted "neighbours stop sharing an exact edge" trade-off Hexagonal's own Jitter already makes, rather than the more involved shared-lattice-vertex jitter a "real" irregular triangulated mesh would use — deferred as a future refinement, not attempted this round. At Gap 0 / Jitter 0 this tiles edge-to-edge exactly.

**`Rotation` and `Spin mode`/`Spin amount`/`Noise scale` — ported verbatim from Hexagonal**, same session, same request applied to the new generator. `Rotation` (0–60°) is the identical rigid whole-lattice rotation: the triangular lattice is the hexagonal lattice's own dual and shares its 6-fold symmetry, so the field is built in its own unrotated frame (sized from the inner rect's diagonal, centred on its centre), rotated as a whole, then clipped — rotating each triangle's shape alone while leaving lattice points fixed would reopen the same gaps/overlaps Hexagonal's own header explains. `Spin mode` offers the identical five flavours (Random/Checkerboard/Radial/Spiral/Noise), rotating each triangle's own local orientation around its own (jittered) centroid, independent of and composed before the rigid `Rotation` — same "necessarily breaks tiling" trade-off as Jitter. Composition order: jitter (position) → spin (local orientation) → gap (shrink) → rotation (rigid, whole-field) → clip.

**Verified**: Gap 0 is an exact edge-to-edge no-op (clean zig-zag boundary, single de-duplicated lines, correctly clipped on all four sides — no overflow past the inner rect); Jitter 0.5 produces a genuinely distinct scattered-triangle texture; Rotation 0 reproduces the pre-Rotation render exactly (170 cells, identical layout); Rotation 30 still tiles perfectly edge-to-edge at a visibly different diagonal angle; all six Spin modes (Off/Random/Checkerboard/Radial/Spiral/Noise) render distinctly with correct row visibility (Spin amount hidden only at Off, Noise scale shown only at Noise); Noise mode shows the same organic spatially-coherent wobble as Hexagonal's; SVG export real vector geometry (544–576 `<line>`s depending on config); 0 unaccessibly-named controls; all six generators regression-clean with the console watched live through every actual mode switch in the same tab.

### Diamond (`diamond.js`) — geometric

The fifth polygon-shaped generator, and the cleanest illustration yet of "rotate the whole field, never just the shape" — squares built on a PLAIN uniform lattice (no offset math at all, trivially edge-to-edge: `hSpacing = vSpacing = side`), each square's own 4 vertices placed at its corners (45°+90°·i) so `Rotation` 0 reads as a plain axis-aligned square grid and `Rotation` 45 reads as the classic diamond/argyle pattern — one continuous `[0, 90)` control (a square's point-group order is 4, not 6, hence the different period from every other polygon generator here) morphing between what would otherwise be two separate named generators. Ships with `Rotation` defaulting to 45, not 0, so it reads as "Diamond" out of the box per its own name, while still being freely adjustable down to plain squares or anywhere between.

**A real first-draft mistake, caught and rebuilt before ever running the code**: the first attempt built diamond-oriented squares directly on an OFFSET row/column lattice, guessing at spacing by analogy to Hexagonal's own offset-row construction. Re-deriving the geometry by hand (checking where same-row diamonds' vertices actually landed) showed adjacent diamonds only touched at a single VERTEX, not a shared EDGE — real gaps between rows, not a valid tiling, caught by re-checking the reasoning rather than by a failed render. Fixed by dropping the hand-derived diamond-lattice spacing entirely and building what's actually proven to tile — a plain square grid — then applying the exact same "rotate the whole field rigidly" mechanism already proven correct by Hexagonal and Triangular. A rigid rotation of a tiling that already tiles is still a tiling, at any angle, with zero new spacing math to get wrong.

`Spin mode`/`Spin amount`/`Noise scale` are the identical five flavours as Hexagonal/Triangular, ported the same way, applied to each square's local orientation before the rigid Rotation.

**Verified**: Gap 0 is a true edge-to-edge no-op (continuous zig-zag lines throughout, confirmed visually after the lattice-geometry fix — this was the exact property the first draft got wrong); Rotation 0 renders a clean, correctly-counted axis-aligned square grid (81 cells on a 9×9 canvas at the default density); Rotation 45 renders the diamond/argyle pattern; an in-between angle (20°) tiles perfectly with no gaps; Noise Spin mode shows the same organic wobble as the other two generators; SVG export real vector geometry (340 `<line>`s on an 85-cell Noise-spun canvas); 0 unaccessibly-named controls; all seven generators (Bento/Sinusoidal/Voronoi/Hexagonal/Radial/Triangular/Diamond) regression-clean, console watched live through every actual switch.

### Circular (`circular.js`) — geometric

The seventh polygon-shaped generator, and a second first-draft correction caught by Diego rather than by testing: the initial build clipped a plain rect lattice inside a circular BOUNDARY (a grid of squares that happens to sit inside a circle) — wrong, because it means the base CELL shape stayed a square, when every sibling generator's own naming convention is that the cell itself is the named shape (Hexagonal's cells are hexagons, Triangular's are triangles, Diamond's are squares). Rebuilt so each cell genuinely IS a circle: a real circle-packing grid, centres on the identical triangular/hex-packing lattice as Hexagonal's own offset-row construction (not a coincidence — a hexagonal tiling's centre lattice and a circle-packing's centre lattice are the same lattice), with different spacing constants since circles pack point-TANGENT rather than edge-to-edge: same-row centre spacing is the full diameter `d`, row spacing `d·√3⁄2`, odd rows offset by `d/2`.

**Honesty disclosure, the same kind of thing Sinusoidal's own header states for wavy boundaries**: circles cannot truly tessellate the plane the way every other shape in this file set can — at Gap 0 circles touch their neighbours at a single point, not a shared edge, so real triangular voids remain between any three mutually-touching circles. That's correct circle-packing geometry, not a bug — every circle's own outline draws as its own closed `<polygon>`, independently. `Columns` sets the target diameter (`inner.width / cols`); `Gap` shrinks each circle's radius from the touching size. Inner-rect clipping is needed, same reason and same technique as Hexagonal/Triangular/Diamond — boundary circles trim into real partial-disc shapes at the canvas edge.

**Verified**: Gap 0 shows circles genuinely touching (maximum packing, visible triangular voids between neighbours, not overlapping and not gapped); Gap > 0 opens visible space between circles cleanly; SVG export real vector geometry (3579 `<line>`s on a 95-cell canvas — high count is expected and correct, since circles don't share edges to dedup); 0 unaccessibly-named controls; all eight generators (Bento/Sinusoidal/Voronoi/Hexagonal/Radial/Triangular/Diamond/Circular) regression-clean, console watched live through every actual switch.

**`Rotation`/`Jitter`/`Seed`**, added same session per Diego's own follow-up ask. `Rotation` (0–60°, the hex-packing lattice's own period) rigidly rotates the whole lattice of centres, built the identical proven way as Hexagonal/Triangular/Diamond (unrotated frame sized from the inner rect's diagonal, centred on its centre, rotated as a whole, then clipped) — the one honest wrinkle specific to Circular: a circle's own outline is rotationally symmetric, so Rotation never changes an individual cell's SHAPE, only how the rows/columns align relative to the canvas, which changes how the boundary clips (visibly different diagonal cuts at the edges, confirmed at Rotation 30°). `Jitter` offsets each circle's centre by a seeded random amount before clipping, same accepted trade-off as every sibling generator's own Jitter — circles can end up overlapping or unevenly spaced, a hand-scattered "pebble/bubble" look instead of mechanically perfect packing (verified visually at Jitter 0.4).

**Verified**: Rotation 0 reproduces the pre-Rotation render exactly; Rotation 30 still shows circles genuinely touching/round (shape unchanged, only lattice orientation and boundary clipping differ); Jitter 0.4 gives a genuinely distinct organic scattered look; SVG export still real vector geometry (3702 `<line>`s at Jitter 0.4); 0 unaccessibly-named controls; all eight generators regression-clean, console watched live through every actual switch.

## 5. Universal JSON Model (`js/json-model.js`)

```js
{
  version, generatedAt,
  canvas: { width, height, unit, orientation, margin, safeArea, bleed },
  grid: { type, solver, params, gap, padding, cellShape,
          tracks: { cols: [...], rows: [...] } },   // rect grids only
  cells: [ { id, col, row, colSpan, rowSpan } ]      // rect grids
      // OR [ { id, points: [[x,y],...], centroid: [x,y] } ]  — polygon grids (Voronoi)
}
```

`grid.cellShape` (`'rect'` or `'polygon'`) is the fork every renderer branches on. Rect grids deliberately do **not** store per-cell pixel `x/y/width/height` — those are always derivable from `tracks` + spans (`resolveCellRects`), and storing a derived value alongside its source is exactly how "which one is the truth" bugs happen. Polygon grids (Voronoi) have no track lattice at all — there's no meaningful "canonical span" representation for an arbitrary polygon, so their cells carry final absolute-coordinate points directly, resolved once at generation time. The CSS Grid renderer reads `tracks` + spans natively (`grid-template-columns`, `grid-column: n / span k`); SVG/raster/Figma read resolved pixel rects for rect grids, or `cell.points` directly for polygon grids — every renderer reads the same source either way, so none can drift from another.

## 6. Renderers (`js/renderers/`)

- **`html-renderer.js`** — for rect grids, `paintGridDOM` paints the live preview as a *real* `display: grid` container (not absolutely-positioned divs simulating one); `buildHTMLSnippet` serialises the exact same CSS the DOM preview uses, so the on-screen canvas and the exported HTML file can never disagree — the same WYSIWYG rule as every raster/vector renderer elsewhere in Organica, applied to a DOM target instead of a `<canvas>`. For polygon grids (`cellShape === 'polygon'`), both functions branch to `buildPolygonSVG` instead — an embedded SVG preview, since CSS Grid has no honest way to represent an arbitrary polygon cell (§4's own Voronoi section has the full reasoning).
- **`svg-renderer.js`** — one CLOSED shape per cell (`<rect>` for rect grids, `<polygon>` for polygon grids), `fill="none"` by default but a real closed path a design tool can select and fill with a colour, plus a dashed margin guide. **Replaced a de-duplicated-edge-list version** (one `<line>` per unique boundary, never a closed per-cell shape) that Diego caught in real use: opening an exported file, nothing was actually a closed, fillable shape — just independent line segments that happened to line up on screen. The de-dup approach's own original motivation (avoiding a doubled-stroke look where two adjacent cells each draw their own copy of a shared edge) is accepted as a minor cosmetic trade-off now, since it's strictly less important than the shapes being closed and fillable at all. `json-model.js`'s own `collectEdges`/`collectPolygonEdges` were removed as dead code once nothing called them any more.
- **`raster-renderer.js`** — same fix, same reasoning: one closed shape per cell (`strokeRect` for rect grids, a real `beginPath`/`closePath`'d path for polygon grids) onto an offscreen `<canvas>` for PNG export, independent of SVG parsing.
- **Figma** — reuses `Organica.sendToFigma()` and the existing `figma-plugin/` verbatim: the grid arrives as vector guides via the plugin's existing SVG-import path. **Not yet** native Auto Layout frame generation — that's Phase 5 (§7). No UI button calls it currently — the Figma send button was removed product-wide across every Organica tool pending its return as a tab inside the Export popover; `sendToFigma()` stays defined, unwired, ready for that.

## 7. UI shell

Export lives in the shared bottom-centre floating toolbar (`shared/organica-floatbar.css`), not the header — the same component Strata/Spore/Pollen/Halide/Komorebi/Living Path/Genesis Creator/Camo Turing all use; the header carries only the logo and status. Zoom/pan is the shared `Organica.createZoomPan` (`shared/organica-core.js`) on `#canvas-frame` — a pure CSS transform that never touches `canvas.width/height` or the JSON model, so no export can disagree with what's on screen regardless of zoom level. Range is `[0.01, 12]` rather than the function's own `[1, 12]` default (lowered from an initial `0.1` after cm/m canvases could need a fit-scale below that, clamping to `min` and zeroing pan — see the cm/m session note in `CLAUDE.md`), and a canvas whose physical size just changed (a new preset, a manual width/height edit) is auto-fit to the viewport once — Loom renders its canvas at its own real declared size (an A4's 297px up to a 1920px social preset, capped at 50 000 canonical units / 50m), unlike Halide/Komorebi's own capped ~900px preview resolution, so 100% alone isn't guaranteed to fit.
